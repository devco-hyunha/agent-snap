## 결정

- 결정: 모델 항목(`endpoints[].models[]`)에 선택 키 `context_window`를 둔다. 단위는 토큰(정수)이다. 생략하면 **65536**(64K)으로 정규화한다. 값이 있으면 1 이상 정수여야 하며, 0·소수·비숫자는 모델 이름만 밝힌 설정 오류로 거부한다.
- `context_window`는 **클라이언트가 보내는 맥락을 맞출 한도**다. 샘플링의 `max_tokens`(한 번 생성 길이 상한)와 다른 칸이며, 요청 본문에 이 키 이름으로 실지 않는다(02-5 Out). 한도를 써서 오래된 도구 출력을 줄이거나 요약하는 일은 작업 04의 `context`가 맡는다.
- 서버 `/models`의 `context_length` 등으로 설정을 자동 채우지 않는다(02-7 Out 유지). 로컬 서버가 창 크기를 안 알려 주거나 클라이언트가 과대 기본(예: 1M)을 쓰는 경우를 막기 위해 **설정에 적거나 생략 시 64K**를 쓴다.
- 스키마 위치는 D20의 모델 선택 항목에 포함한다. 읽기·검증·예시 반영은 02-2 보강, 저장은 02-8, 사용은 작업 04다. 구현은 02-5~02-7 전송·선택 경로와 섞지 않고, **02-8 전에 02-2 보강**으로 넣는다.

## 근거

- 근거: 로컬 LLM·에이전트 연동에서 컨텍스트를 안 주면 클라이언트가 매우 큰 창(예: 1M)으로 잡는 경우가 있다. 모델마다 실제 창이 다르므로 모델별 설정이 필요하다. 생략 기본 64K는 흔한 로컬 창에 가깝고, 과대 기본보다 안전하다. 키 이름 `context_window`는 업계에서 쓰는 “컨텍스트 윈도우”와 같고 `max_tokens`와 혼동하기 어렵다. `max_context`는 짧지만 생성 상한과 이름이 겹치기 쉽다.

## 다시 볼 점

- 다시 볼 점: 작업 06 실사용에서 64K 기본이 너무 작거나 크면 기본값을 다시 본다. 작업 03 단발 호출이 같은 한도를 쓰는지 착수 시 확인한다.
