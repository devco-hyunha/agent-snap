## D9와 D22 경계 (격리 vs 신뢰성)

| 구분 | D9 (본 문서) | D22 ([실행 신뢰성과 자율성](D22-execution-reliability-autonomy.md)) |
|------|----------------|----------------------------------------------------------------------|
| 범위 | 실행 **격리**(샌드박스·AppContainer·Job Object로 **환경** 제한) | 실행 **신뢰성**(deadline, 프로세스 트리 정리, 승인 대기 상한) |
| M1/03 | 격리 **방식 보류**; 작업 폴더 경계·비밀 파일 차단·run_command 실행 전 확인은 **현행 유지** | 신뢰성은 M1/작업 03에서 **항상** (셸·승인·네트워크 deadline, 트리 정리) |
| Job Object | 격리 후보 중 하나로 **미확정** | **프로세스 트리 종료** 수단으로 우선 검토 (격리와 목적 분리) |
| 승인 | 승인 **정책**·에이전트별 승인 여부 비교는 조사 맥락; 격리 확정 후 03에 문 유형 반영 | **승인 deadline**·CommandApprover·L1~L3 **자율성** 단계 |

- 프로세스 트리 정리·셸 deadline·승인 응답 deadline은 **D22** 신뢰성 기본으로 다룬다.
- AppContainer·낮은 무결성 수준·제한 토큰 등 **실행 격리**는 **D9**에서 계속 보류한다.

## 결정

- 결정: 작업 03은 현재 정책(작업 폴더 경계, 비밀 파일 차단, run_command 실행 전 확인)을 유지하고, 실행 격리 방식은 보류한다. 도구별 일방향/양방향 문 유형 분류는 격리 방식이 정해진 뒤 03에 반영한다.

## 근거

- 근거: snap은 가능한 한 경량을 목표로 한다. Docker, WSL, 별도 프로그램 설치, Windows Pro 이상 기능처럼 사용 제약과 불편을 늘리는 방식은 맞지 않는다. snap에 넣는 것은 라이선스를 확인해야 한다(2026-10-30 사용자 결정). 주요 코딩 에이전트도 파일 쓰기 승인 여부가 갈리고, 승인을 받지 않는 쪽은 되돌리기나 샌드박스로 보완한다(RESEARCH.md 작업 03 비교 항목).

## 다시 볼 점

- 다시 볼 점: 후보는 Windows 기본 프로세스 격리 기능(낮은 무결성 수준, AppContainer, 제한 토큰, Job Object)과 snap 자체의 쓰기 전 스냅샷이다. Home 에디션 동작, 셸 자식 프로세스까지 격리되는지, Rust 바인딩 크레이트의 라이선스는 확인하지 않았다. 프로세스 트리 정리·셸 deadline·승인 응답 deadline은 격리와 분리해 D22의 신뢰성 기본으로 다루고(`docs/decisions/D22-execution-reliability-autonomy.md`), AppContainer 등 실행 격리는 계속 보류한다.
