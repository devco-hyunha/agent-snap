## 결정

- 결정 1 (전환 주체): 2안 전환은 03-2 루프 안에서 형식을 고르는 상태로 둔다. 루프는 `ToolCallFormat`(1안 `Openai`·2안 `Text`) 상태를 왕복 조립에서 고르고, 4x와 텍스트 2회 연속에서 `tools` 배열을 빼고 2안 조립을 붙인다. 2안 조립·복원·전달 모듈은 03-4가 만든다(SRP 경계 유지). 바깥에서 루프를 다시 여는 래퍼 방식은 쓰지 않는다(사용자 판단 2026-11-10: 전환 후 대화가 길어지는 자리에서 사용성이 떨어지는 이유로 2안 채택).
- 결정 2 (1회 텍스트 규격): 텍스트 1회 응답은 03-2 AC 1대로 정상 종료하되 전환 후보 값(`FallbackPoint::NoToolCallText`)만 기록에 남긴다. 전환 확정은 2회 연속에서 한다. spec의 "1회면 전환"과 "2회 연속 전환" 문장 모순은 결정 2로 정리한다.
- 결정 3 (감지 우선순위): 선언 → 감지 순을 따른다. `tool_call_form`이 `openai`·`text`면 선언대로 쓰고 감지하지 않는다. `auto`일 때만 4x 상태 코드 표(`agent/fallback.rs`)로 감지한다. 응답 본문 글자·`type` 필드 판별은 금지 규칙(D28)을 유지한다(서버마다 코드·`type`이 제각각 — llama.cpp는 400 `code`/`type`, mlx-lm은 404). llama.cpp `GET /props` 사전 점검은 코드 경로가 아니라 안내 문서에만 적는다.
- 결정 4 (복원 래더): assistant 내용 글자에서 ① Markdown 코드블럭 둘레 제거 → ② 중괄호로 묶인 객체 찾아내기 → ③ 파싱 → ④ 실패 시 `agent/args.rs`의 `recover_arguments`(닫힘 기호 1회 복구) 재사용 → ⑤ `Tool::parameters_schema` 검증 → ⑥ 모호하면 거부하고 짧은 오류로 알린다(2609.07370 5절·7절 권고). ①·②는 코드에 없는 단계라 03-4가 새 파일에서 만들고, spec의 옛 포인터 `provider/args.rs`는 실재하지 않는 경로라 `agent/args.rs`로 정정한다.
- 결정 5 (이어쓰기): 1안 왕복에서 쌓은 messages(시스템·user·assistant·tool)를 그대로 두고 2안 줄만 새로 붙인다. 2안 assistant 줄은 `tool_calls` 없이 내용만 담고 도구 결과는 `role: user` 글자로 붙인다. 같은 요청 재시도는 02-6 한 층만 거친다(D13 유지).
- 결정 6 (기록 자리): 전환·복귀 기록은 03-2가 만든 `ToolCallRecord.format`·`LoopResult.fallback_point` 자리에 남긴다. 파일 로그 기록(세션 로그)은 04 배치라 03-4 범위 밖이다(`snap-core`에 `logs` 자리는 없다 — 검색 0건 확인).
- 결정 7 (설정 칸): `ModelConfig`에 `tool_call_form`(`openai` 기본·`text`·`auto`)를 더한다. 읽기(`config/read/parse.rs`)·저장(`config/save/check.rs`·`config/save/config.rs`)·기본값·예시 파일(`agent-snap.example.jsonc`)을 같은 작업에서 고치고, D20 정본의 선택 목록에 같은 항목을 더한다. D29 `context_window`가 지난 자리 규칙과 같고 표준 2단계(구현 서브→독립 리뷰)로 다룬다.
- 결정 8 (프롬프트 규격·범위 유지): 2안 지시문에 "JSON" 글자를 명시하고 도구가 20개를 넘으면 등록 안내를 남긴다(OpenAI 공식 안내). 스키마 글자 압축(TSCG 2605.04107)은 읽는 쪽 절감 근거가 있어 06 실측 후 후보로 두고 이번 AC에 넣지 않는다. 답 형식은 JSON 유지.

## 근거

- 업계 관례 조사(2026-11-10, [12번 문서 8절](../research/12-tool-calling-forms.md)): OpenCode·LiteLLM·Vercel AI SDK가 전부 사전 선언형(카탈로그·캐퍼빌리티 표·조회 함수)을 기본으로 쓰고, 4xx 후 "tools 제거 재시도"는 공개된 문서가 없으며 형식 고정 재시도(`requireAssistantAfterTool`)만 확인.
- llama.cpp·vLLM·mlx-lm 실무 함정(12번 8절): 상태 코드와 `type`이 서버마다 불일치, `tool_call_id` 재투입 400(llama.cpp 이슈 #26359, mlx-lm 이슈 #1375), 과도한 KV 양자화(`-ctk q4_0`)의 도구 호출 성능 저하.
- 2609.07370 감사 주의(12번 8절): 4.4절 "실패 658개"가 표 2 합계와 계산이 어긋난다는 외부 감사(sunny34.com)가 있어 준수율 인용은 표 2·표 3만 쓴다.
- 사용자 판단(2026-11-10): 전환 주체는 래퍼가 아니라 루프 확장(2안) — 03-2 결정 문서 첨삭 + 03-4에서 추가 작업으로 진행.

## 보정 근거 (2026-11-10 리서치 서브 직접 확인, 12번 문서 9절)

- (a) 2609.07370 표 2·표 3 재확인: 수치는 계획과 같고, 파서 기준 순서(펜 제거 → 중괄호 추출 → 파싱 → 이름·필수 인자 대조)도 우리 래더 ①~⑤와 같다. 표 3은 복원 성공 시 정답률이 높고 파서 부담이 복원 실패에 몰리므로, 복원 실패 시 짧은 오류 재시도 권고(AC 4와 별개)가 정당하다.
- (b) TSCG E4 분해(R² 0.88→0.03): 소형 모델 이득은 "압축"이 아니라 "JSON→글자 형식 변환"에서 나오고 순수 압축 이득은 0에 가깝다. 2605.26165(8K에서 JSON 스키마가 창을 넘쳐 EM 2.6% → 절감 시 +20.5pp)가 2안 프롬프트 길이 리스크를 뒷받침한다. 읽기 쪽 절감은 06 후보로만 둔다(답은 JSON 유지 원칙 그대로).
- (d) 새 함정: 툴 역할 메시지에 레거시 `name`을 넣으면 엄격한 OpenAI 호환 프록시가 400으로 거절(hermes-agent PR #99254). GGUF 템플릿이 `tool` 역할을 못 읽으면 예외가 남(openclaw #27406) → 결정 5의 `role: user` 전달이 로컬 관례에 맞음을 확인. 우리 `ChatMessage`에는 `name` 칸이 없어 해당 없음.
- (c)(e) 관례 재확인: 여러 호출을 한 번에 뽑는 것이 관례(OpenAI 가이드·vLLM·smolagents PR #1906) → 2안은 1개부터, 2개 이상은 06 판단 유지. 선언형 캐퍼빌리티가 기본(OpenCode·LiteLLM, PR #30032는 기본값 False로 이행) → 선언 우선 → `auto`만 감지 유지.

## 다시 볼 점

- `tool_call_id` 재투입 400 함정(9자리 알파뉴머릭 규칙)은 03-4 구현에서 id 생성 규칙을 정하고, 실측 확인은 06에서 본다. llama.cpp는 32자 id를 계속 만들고(이슈 #26359 stale 닫힘·미합병), mlx-lm PR #1399(9자리 축소)도 미합병이라 생성 규칙을 우리 쪽에서 정해야 한다는 근거가 늘었다(12번 9절 (d)).
- TSCG(스키마 압축)·TOON(읽기 쪽 절감) 채택 여부는 06 실측(전환율·프롬프트 길이) 후 별도 기획으로 판단한다.
- 06 실사용에서 4x 코드 표(400·404·405·406·415·422·501)에 걸리지 않는 서버가 나오면 `auto` 감지 표를 다시 본다.
- 선언형 캐퍼빌리티(`capabilities.tools`)를 설정 칸으로 더 넓힐지는 03-4 착수 결과와 06 데이터를 보고 판단한다.
