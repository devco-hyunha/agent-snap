## 1. 코드 검색 RAG (코딩 에이전트)

- Practical Code RAG at Scale
  - 링크: https://arxiv.org/abs/2510.20609 (JetBrains Research)
  - 핵심: 코드 작성 태그에서는 BM25+단위 나누기가 가장 정확하고 10배 빠르다. 자연어→코드 버그 찾기는 임베딩이 우위(속도 100배 느림). 32–64줄 덩어가 작은 맥락에 최적.
  - snap 관련: 로컬 모델용 agent-snap은 BM25·grep 기본, 임베딩은 보조.
- SpIDER: Spatially Informed Dense Embedding Retrieval
  - 링크: https://arxiv.org/abs/2512.16956 (Johns Hopkins·AWS AI Labs)
  - 핵심: 임베딩 검색에 코드 그래프 탐색과 LLM 걸러내기를 얹어 Recall@20을 13~27% 높임. 그래프는 세션 시작 때 온디맨드 생성.
  - snap 관련: 04 세션 검색 보강 설계 참고.
- ContextBench: A Benchmark for Context Retrieval in Coding Agents
  - 링크: https://arxiv.org/abs/2602.05892 (Nanjing Univ·UCL)
  - 핵심: 1,136개 작업에서 에이전트가 "찾은" 컨텍스트를 추적·측정. 찾았으나 안 쓴 간극이 큼.
  - snap 관련: 05 검색 계통 측정 지표 설계에 활용.
- VITAL-RAG: Invariance Race for Context Allocation in Coding Agents
  - 링크: https://arxiv.org/abs/2607.26937
  - 핵심: 코드 대상(함수·클래스) 단위로 중복을 없애고 토큰 예산 배분. Recall@4K 39.59→63.67%, 토큰 35.63% 감소.
  - snap 관련: 04 컴팩트화 규칙 설계에 활용.
- Why Grep Beat Embeddings (기사·비논문)
  - 링크: https://jxnl.co/writing/2025-09-11/why-grep-beat-embeddings-in-our-swe-bench-agent-lessons-from-augment/
  - 핵심: 에이전트가 grep을 직접 쓰게 하니 임베딩 RAG보다 낫다.
- SWE-grep (비논문)
  - 링크: https://cognition.com/blog/swe-grep
  - 핵심: 병렬 검색 특화 모델, 같은 등급 속도.
  - snap 관련: 에이전트 주도 검색(03 grep 도구) 우선 채택 근거.

  - 링크: https://arxiv.org/abs/2606.11680

## 5. 지시 파일 색인 관리 설계 제안 (2026-11-07 사용자 제안, 2026-11-08 3차 교정까지 반영)

- 배경: Claude는 스킬 사용 시 파일마다 앞 100줄만 열어 필요한 스킬인지 확인한다. 그래서 스킬 상단에 명세(프론테이터) 작성을 권한다. 여러 파일을 여는 방식 자체를 snap은 바꾸고 싶어 한다.
- 제안: 에이전트가 관리하는 **색인 파일**을 둔다. 스킬·프롬프트·규칙 파일의 목록·요약·경로를 한 파일에 모는다. 에이전트는 색인 하나만 읽고 필요한 파일을 골라 한 번만 읽는다.
- 2차 교정 (2026-11-07 사용자 지적 반영):
  - 지적 1: frontmatter만 관리하면 색인 파일의 목적이 사라진다. 색인 파일은 Claude가 스킬마다 100줄씩 여는 일을 없애려고 만드는 것이다. frontmatter 유무와 상관없이 파일 **내용에서 생성한 요약**을 색인에 담는다.
  - 지적 2: frontmatter가 없다고 스킬을 걸러내서는 안 된다. frontmatter는 옵션이고, 없으면 파일 내용(제목·서두·본문)을 읽고 요약을 만든다. frontmatter는 요약의 보조 신호일 뿐 필수 규격이 아니다.
  - 지적 3: "어긋남 표시만"은 어긋난 스킬을 사실상 배제한다. 표시로 끝내지 않고 **그 파일 내용을 읽어서 색인 내용을 바꾼다**. 어긋남 = 재스캔 대상.
- 3차 교정 (2026-11-08 사용자 지적 반영):
  - 지적 1: 대상은 스킬만 아니다. **하네스 규칙·프롬프트·AGENTS.md·CLAUDE.md·rules 파일까지 포함하는 "지시 파일 색인"** 이다. 하네스·감시·세션 규칙을 전달하는 모든 경로가 이 색인을 통과한다.
  - 지적 2: 우선순위 규칙. **사용자가 지정한 것은 우선순위로 필수 전달** 한다.
  - 지적 3: git 의존 폐기. 색인 위치가 git 저장소 추적 밖에 있어도 git에 의존하지 않는다. 변경 감지는 git 상태 비교가 아니라 **snap 파일 조회·mtime·크기·해시 기록 비교**로 한다 (git 비교는 폐기).
- 설계:
  - 색인 대상: 스킬, 하네스 규칙, 사용자 지정 규칙(AGENTS.md·CLAUDE.md·rules 파일), prompt 파일, 그 밖의 지시 파일.
  - 색인 항목: 이름, 경로, 한 줄 요약(파일 내용에서 생성), 트리거 키워드(파일 확장자·폴더명·작업 유형), 파일 조회 기록(mtime·크기·해시), 전달 우선순위 플래그. 형식은 jsonc로 확정(2026-11-07 사용자 선택).
  - 생성 방식: 에이전트(스캐너)가 지시 파일을 열어 내용을 읽고 한 줄 요약과 트리거를 만든다. 파일 앞부분만 여는 Claude 방식과 달리, 색인 한 장만 열고 판단한다. frontmatter가 있으면 요약을 그 설명과 맞춰 채운다.
  - 파악 순서: ① 색인 한 장 열기 → ② 현재 작업과 요약·트리거로 후보 고르기 → ③ 선택한 파일 본문만 읽기.
- 전달 우선순위 (사용자 지정 규칙, 2026-11-08 지적 2):
  - 사용자가 지정한 것은 우선순위로 필수 전달한다. 플래그가 `always`인 파일(AGENTS.md·rules·하네스 규칙)은 매 세션 전달에 꼭 넣는다. (D36 3번 "불변 규범은 push"와 같은 방향)
  - `on-demand`(필요할 때): 색인에서 후보로 골라 필요 시 전달.
  - `user-pinned`(사용자가 지정): 색인 플래그와 별개로 사용자가 지정하는 규칙은 색인 우선순위와 별개로 항상 1순위다. 지정은 색인이 아니라 세션 쪽에 담는다(2026-11-08 4차 교정: 세션별 지정, 5-1절 참조).
- 색인 갱신 시점 (git 의존 폐기, 2026-11-08 지적 3):
  - 기본은 **세션 시작 스캔 + 파일 읽기 직전 확인**. 분 단위·시간 단위 스케줄은 설정으로 켜는 옵션.
  - 변경 감지는 snap이 직접 한다: 파일 목록 조회 → mtime·크기·해시를 색인에 기록 → 이전 기록과 비교해 추가·삭제·수정 파악 → 바뀐 파일만 열어 요약 재생성. git은 쓰지 않는다. 색인 위치가 git 저장소 밖에 있어도 같은 방식으로 동작한다.
  - 어긋남 처리: 표시만 남기지 않는다. 추가→신규 항목, 삭제→항목 제거, 수정→요약 재생성. 표시로 끝내지 않는다.
  - 색인 쓰기는 캐시 갱신이고 원본을 바꾸는 일이 아니다. 스캐너의 색인 갱신은 게이트 없이 자동으로 두고, 색인 자체가 파생 캐시임을 문서에 적는다(04 착수 시 최종 확정).
- 관련 연구: Claude skills 3단계 점진 공개(①항상 ②조건 시 ③첨부)는 "항상 실리는 메타데이터"를 1개 색인으로 압축한 형태다. OKF의 개념 파일·링크 구조와 같은 모양으로 맞출 수 있다. Mem0·HORMA의 요약 색인 → 원본 승격 규칙과 같은 구조(색인 → 필요 시 원문 읽기).
- 배치: D43에 따라 04. 03은 기본 도구만 하므로 색인 스캐너는 04 세부 작업.
- 여는 질문 (04 착수 시): 스캔 주기 기본을 세션 시작 + 읽기 직전으로 둘지, 분·시간 단위 스케줄을 기본으로 둘지. (git 비교는 폐기 확정, 2026-11-08)

## 5-1. 효과 검토 (2026-11-08 사용자 요청)

- 결론: 이 방식은 (1) 스킬·규칙 **선정 단계**에서 토큰과 도구 호출을 크게 줄인다. (2) 토글(스킬 켜기/끄기)은 색인 파일 한 곳의 플래그 한 줄로 관리할 수 있다. (3) 단, 토큰 절감의 완전한 근거는 Claude가 공개한 수치가 아니라 snap 추정이다.

### 근거 (Claude Code 공식 문서, 2026-11-08 확인)
- 링크: https://code.claude.com/docs/en/skills
- 스킬 설명(description)은 세션에 **항상 컨텍스트로 실린다. 전체 본문은 부를 때만** 읽는다.
- `disable-model-invocation: true`를 켠 스킬은 설명이 컨텍스트에서 빠진다. `user-invocable: false`는 모델만 부름.
- 한 번 부른 스킬 본문은 대화 턴에 계속 남는다(재요약 시 스킬당 처음 5,000토큰, 합산 25,000토큰 예산 안에 다시 붙임).
- SKILL.md 본문 500줄 이하 권고.
- `skillOverrides` 설정이 스킬 가시성을 파일 수정 없이 설정 파일(`.claude/settings.local.json`)에서 제어한다. `/skills` 메뉴에서 Space로 상태 순환 → 저장.

### 비교 추정 (snap 설계 가정: 100줄 1회 열기 ≈ 150토큰, 색인 항목 1개 ≈ 50토큰, 2026-11-08 사용자 선택)
- Claude 관측 방식("스킬마다 100줄 열어 확인") 20개: 도구 호출 20회 + 약 3,000토큰(150×20).
- snap 색인: 색인 1회 열기 + 약 1,000토큰(50×20) + 도구 호출 1회.
- 선택 단계: 도구 호출 20회→1회, 토큰 3,000→1,000로 약 67% 절감. 색인 항목 요약이 길어지거나 트리가 세밀해지면 항목당 50토큰이 커지므로 절감률이 작아진다. 역으로 스킬 수가 적으면(2~3개) 색인 이득이 작다. **색인 1장 토큰이 스킬 N개 100줄 열기 합계보다 작은지가 절감의 조건**.
- 절감은 선택·탐색 단계만이다. 스킬 본문 1장(선택 후 읽는 100~500줄)과 호출된 뒤 턴에 남는 본문 비용은 색인이 줄이지 못한다. 이 둘은 Claude와 같고, 색인 방식만의 절감이 아니다.
- 효과는 스킬 수가 많을수록 커지고, 적으면 이득이 작다.
- 색인 파일은 매 턴 실리는 게 아니라 **필요 시 여는 캐시 파일**이다. 세션 시작 스캔은 토큰 비용이 아니라 도구 호출 시간 비용이다. 색인 생성은 파일당 1회 읽고 요약 만드는 비용이며 매 스캔마다 재사용(변경 파일만 재스캔).

### 강제 적용 토글 연결 설계 (2026-11-08 2단계 교정: 세션별 지정)
- 사용자 지적: 토글을 색인 항목에서만 관리하면 세션마다 다른 지정이 필요한데 편차가 심해진다. 색인 토글은 **기본값**으로 두고, 세션마다 지정은 별도로 둔다.
- 2층 구조:
  - 1층 색인 기본값: 파일별로 `always`·`on-demand`·`off` 기본 플래그를 색인이 가진다. 색인은 파일의 성격(언제 쓸 파일인가)만 기록한다.
  - 2층 세션 지정: 세션이 열 때 사용자가 지정한 규칙·스킬은 세션 기록(jsonl)이나 세션 설정에 담는다. 색인을 고치지 않는다. 세션마다 `user-pinned`(강제 1순위)를 자유롭게 지정할 수 있다.
- 우선순위: 세션 지정 > 색인 기본값. 세션에서 `off`로 지정하면 색인 기본이 `always`여도 그 세션에서는 빠진다. 반대로 세션에서 `user-pinned`로 지정하면 색인 기본이 `on-demand`여도 1순위로 전달한다.
- 토글 변경 반영: 색인 기본값 변경은 색인 갱신 직후, 세션 지정은 그 세션에 즉시 반영. 두 경로를 분리해 색인 파일의 편차(세션별 지정이 색인에 쌓이는 문제)를 없앤다.
- 근거 비교: Claude Code는 스킬 1개씩 frontmatter를 고치거나 settings 파일(`skillOverrides`)로 전역 제어만 한다. snap은 파일 기본값(색인)과 세션 지정(세션 기록)을 분리해 Claude에 없는 "세션 단위 토글"을 처음으로 제공한다.

## 6. EvoHarness-RL (확인만)

- 링크: https://arxiv.org/abs/2608.05446, https://evoharnessrl.github.io, https://github.com/EvoHarnessRL/EvoHarness-RL (v2 제목 "Learning Runtime Harness Coordination for Self-Evolving Agents")
- 핵심: BPE(Belief=환경 사실, Progress=하위목표 상태, Experience=작업 간 재사용 지식) 워크스페이스를 4개 메타동작(track·commit·recall·note)으로 노출. Base 스캐폴드로 최대 모델 성공률 +10.0%p, RL로 최고 오픈소스 대비 +8.5%p.
- snap 관련: D36에 기록된 BPE가 동일. 세션 임시 문서·메모리 규칙에 3역할 매핑 가능.
