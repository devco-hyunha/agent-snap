# 02-6 재시도 적용: 명세

- 상태: 완료 (T1~T7 구현·리뷰 PASS. 작업 단위 전체 리뷰 PASS — AC 8종 시험 확인)
- 상위 문서: [plan.md](plan.md)
- 선행 결정: 10번(한 층 재시도·Full Jitter), 12번(비대상·매핑·판정 우선순위), 14번(전송 크레이트)
- 매핑 정본: [02-4 spec.md](../04/spec.md)의 「02-5 전송 오류 → 02-4 입력 매핑」 표. 이 문서는 그 표를 적용한 결과만 적는다.

## 입력과 출력

- 입력
  - 안쪽 클라이언트: 02-5의 `HttpTransport`처럼 `LlmClient`를 구현한 것 하나.
  - 재시도 설정: 02-2의 `http` 값(재시도 횟수, 백오프 최소·최대, `Retry-After` 상한).
  - 난수 공급(주입).
  - 취소 토큰(02-5와 같은 토큰).
- 출력: 스트림 수신자. 재시도 끝에 성공하면 그 수신자, 포기가 정해지면 재시도하지 않고 안쪽 클라이언트가 낸 오류.
- 재시도 래퍼는 `LlmClient` 트레이트를 구현한다. 에이전트 루프는 안쪽 클라이언트와 같은 방식으로 쓴다.

## 동작 규칙

### 재시도 지점

- 재시도는 `open` 단계(요청을 보내고 응답 헤더를 받기 전) 실패에서만 한다.
- 헤더를 받은 뒤 생긴 실패(스트림 유휴 초과, 헤더 이후 본문 읽기 실패, 서버 오류 청크, 형식 오류, 취소, 끝난 스트림에 대한 조각 거부)는 02-4 판단에 넣지 않고 그대로 돌려준다.
- 스트림 조각을 하나라도 소비한 뒤에는 요청을 재생하지 않는다. 근거: OpenAI Rate limits guide의 "don't automatically replay a request after consuming output".

### 판단 따라가기

- 02-5 전송 오류를 02-4 spec 매핑 표대로 02-4 입력으로 옮긴 뒤 `decide_retry`를 부른다. 판단 규칙은 고치지 않고 부르기만 한다.
- 판단이 재시도(대기)를 주면 그 시간만큼 기다린 뒤 같은 요청을 다시 연다.
- 판단이 포기를 주면 재시도하지 않고 안쪽 클라이언트의 오류를 그대로 돌려준다.
- 상태 오류에 서버가 준 `Retry-After` 헤더 값이 있으면 판단에 그 값을 넘긴다. 헤더가 없으면 없는 것으로 넘긴다.
- 시도 횟수는 첫 요청을 1로 센다.

### 백오프 대기

- 대기는 tokio의 시간 대기와 취소 토큰을 `select!`(biased)로 경합해 잰다.
- 취소가 먼저 오면 대기하지 않고 취소 오류로 끝난다.
- 대기가 끝나면 다음 시도를 연다.

### 설정 변환

- 02-2의 `http` 값(f64 초)을 02-4가 받는 `RetrySettings`(Duration·정수)로 바꾼다. 변환은 래퍼가 만든다.
- 02-4가 요구하는 `RandomSource`의 상용 구현을 제품 코드에 둔다. 새 난수 크레이트는 의존하지 않는다.

## 오류 종류와 담는 것

| 오류 | 담는 것 | 담지 않는 것 |
|---|---|---|
| 재시도 끝에 포기 | 안쪽 클라이언트가 낸 오류 그대로 | 키, base_url 호스트 |
| 백오프 대기 중 취소 | 취소됨 | 키, base_url 호스트 |
| 상태 오류 확장분 | HTTP 상태 코드, 가린 요약, `Retry-After` 헤더 값 | 키, base_url 호스트 |

- 재시도 래퍼가 새로 만드는 오류는 취소뿐이다. 나머지는 안쪽 클라이언트의 오류를 그대로 쓴다.

## 기본값

02-2 spec의 `http` 기본값: 재시도 3회, 백오프 1~30초, `Retry-After` 상한 60초. 테스트는 짧은 시험용 값을 준다.

## AC

1. Given 모의 서버가 첫 요청에서 429를 `Retry-After`(초 형식)과 함께 보내고 두 번째 요청에서 정상 스트림을 보낼 때, When 래퍼로 스트림을 열면, Then 그 헤더 값이 02-4 판단에 전달되어 그 시간 뒤에 다시 열리고, 최종 결과는 02-5와 같은 성공 스트림이다.
2. Given 헤더 전 연결 실패(6종)를 모의 서버가 만들 때, When 래퍼로 열면, Then 02-4가 후보로 판단한 종류는 설정 횟수 안에서 다시 열고, 후보가 아닌 실패는 다시 열지 않고 안쪽 오류를 그대로 돌려준다.
3. Given 헤더를 받은 뒤 스트림이 멈춰 유휴 초과가 날 때, When 래퍼로 열면, Then 재시도하지 않고 유휴 초과 오류를 그대로 돌려준다(모의 서버가 받은 요청은 1건).
4. Given 스트림 조각을 소비한 뒤 서버가 오류 청크를 보낼 때, When 래퍼로 열면, Then 요청을 재생하지 않고 그 스트림 오류를 그대로 돌려준다(모의 서버가 받은 요청은 1건).
5. Given 백오프 대기 중에 취소 토큰을 켤 때, When 래퍼로 열면, Then 대기를 다 채우지 않고 취소 오류로 끝나고, 이후 요청이 늘지 않는다.
6. Given 최대 재시도 횟수를 넘길 때, When 래퍼로 열면, Then 재시도하지 않고 안쪽 오류를 그대로 돌려준다.
7. Given 재시도 경로가 만든 오류의 Display·Debug를 확인할 때, Then 키와 base_url 호스트가 없다.
8. Given 헤더를 받은 뒤 서버가 본문 끝 표시 없이 연결을 급히 끊어 조각 읽기가 실패로 끝날 때, When 래퍼로 열면, Then 요청을 재생하지 않고 헤더 이후 읽기 실패 오류를 그대로 돌려준다(모의 서버가 받은 요청은 1건). AC 3·4·8은 모두 「헤더를 받은 뒤 실패는 재시도 대상이 아니다」의 같은 경계를 본다.

## 시험 계획

- 모의 서버(02-5 재료 재사용)로 429 + `Retry-After`, 503, 헤더 전 연결 실패, 스트림 중 오류, 헤더 이후 본문 급중단을 만들고 요청 접수 횟수를 센다.
- 난수는 값이 고정된 시험용 공급을 쓴다.
- 시간 값은 짧은 시험용 값을 주고, 경과 시간은 넉넉한 하한·상한으로만 확인한다.
- 네트워크 없이(루프백 모의 서버) 시험한다.
