# project-plan-harness (프로젝트 기획)

결론: 사용자 요청 없이 시작하지 않는다. 사람이 OK 하기 전 다음 칸·디자인 툴·웹 크래프트(ui·컴포넌트 이후)·구현을 하지 않는다.

## 시작
1. 기획 요청인지 본다. 이미 충분하거나 사용자가 기획 불필요면 끼어들지 않는다. 카피만이면 plan-harness/짧은 수정.
2. 크기·종류를 쉬운 선택지로 묻고 사용자가 고른다: 새로 시작 / 추가분만 / 역기획 / 역기획+기획 / 작은 기획.
3. `docs/product/`가 있으면 읽고 → 고칠 곳 제안 → 사용자가 고른 부분만 수정.
4. 이번엔 문서만 / ui·컴포넌트까지를 쉬운 선택지로 확인한다. ui·컴포넌트는 요청에 있을 때만.

## 작성·질문
- 고객·비개발자도 고르게 쉬운 말로 쓴다. 용어는 첫 등장에 풀이한다. 선택지에 “무엇이 달라지는지” 한 줄을 붙인다.
- 질문은 필요할 때까지 배치로 이어서 묻는다. 배치 개수는 끝 조건이 아니다. 선택지 개수 제한 없음. 답만으로 구현하지 않는다.
- 「가정으로 진행」은 잡무·비결정만. 결정은 사용자. 권고를 동의 없이 확정하지 않는다.
- 사용자에게 「잠금」이라 하지 않는다. 「여기까지 확인·합의가 끝나기 전」「사람이 OK 하기 전」「확정하기 전」을 쓴다.

## 칸 (사람 확인 전 다음 금지)
1. 착수 — 왜 / 무엇을 / 하게 할지(+상태·제약·가정·성공·승인자).
2. 조사 — 기본 얇게. 필요할 때만 두껍게. 결과도 쉬운 말.
3. 이번에 풀 문제 — 누구·뭐가 힘든지·왜 지금·성공하면·이번엔 안 함. 확인 전 화면·해법으로 새지 않음.
4. 요구 — 하는/안 하는 일·화면·흐름·상태·정책·예외·측정·지금/다음/나중·가정·아직 미정·통과 조건. 이번 크기 칸만. 안 쓰는 칸은 ‘이번 범위 밖/해당 없음’. `docs/product/`(`main.md`, 커지면 쪼개기). 사람 리뷰.
5. 흐름 검증 — 문서 없으면 시작 금지. 글·표 기본. 어렵면 그림·보드 초안을 제안하고 넣을지는 사용자가 고른다. 화면 목록 승인 → 흐름마다 대조 → 흐름마다 STOP(여기서 멈추고 사람 확인). 발명·예쁜 시안·코드 금지.
6. ui·컴포넌트 정리 — 요청 시에만 `docs/product/ui/`. 무엇이 필요한지·어디에 놓이는지·묶기·생김새·누르면/보이면 하는 일·공통/차이·해도 됨/안 됨. 사람 확인 전 Figma·FigCraft·Storybook·웹 크래프트 선행 금지.
7. 개발 작업 문서로 넘기기 — 위가 사람 확인되면 plan-harness용 초안 + 「이대로 개발 기획 승인할까요?」. 그 승인 전 구현 금지. product·흐름·`docs/product/ui/` 경로를 칸에 채움.

## 보드·경계·원문
- 본체: 무엇을 묻고·남기고·어디서 멈추는지 + 글/표/그림 규칙. 도구 절차는 복붙하지 않는다.
- API 어댑터: `adapters/figma.md`, `adapters/figcraft.md` (보드를 쓰기로 골랐을 때만).
- Out: 예쁜 시안·토큰 표·디자인 시스템 완성·코드 자동 생성·Storybook 본체·구현 할 일 목록·plan-harness 흡수. 프로젝트 기획과 웹 크래프트 병렬 금지. 웹 크래프트는 ui·컴포넌트 사람 확인 후.
- 칸 상세·원문 포인터: `references/lanes.md`. 색인 `docs/research/planning-harness-sources/`는 이 저장소 전용 참고(소비 설치에 포함되지 않음).
