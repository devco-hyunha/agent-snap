# delegation-brief (서브에이전트 요청 규격)

결론: 서브는 대화 맥락과 하네스가 없다. 프롬프트 앞·끝에 개발 하네스(가드레일 6줄·자기점검 4줄)를 반드시 넣고, 작업 문서 본문만 경로 포인터로 대신한다.

## 원칙
- 서브는 대화 맥락과 하네스가 없다. 그래서 하네스 가드레일을 프롬프트 앞과 끝에 직접 넣는다.
- 작업 문서는 docs/tasks/<순번>-<작업명>.md 하나다(plan-harness). 별도 brief-N.md는 만들지 않는다.
- 작업별 범위·금지 사항·산출물·검증 명령은 그 문서의 각 작업 절에 적는다. 범위 밖 파일, 커밋·푸시, 임시 스크립트는 금지한다.
- 모든 에이전트는 파일 삭제 요청·수행·보고 시 해당 파일이 무엇인지, 삭제 이유와 근거가 무엇인지 반드시 설명한다.
- 프롬프트에 작업 문서 본문을 다시 적지 않는다. 하네스 사본은 프롬프트에만 둔다. 구조화 도구에 넣을 때는 해당 이스케이프를 따른다.

## 구현·보정 프롬프트 (포인터 샌드위치, 채운 뒤 500자 이하)
`
[가드레일]
1. 존댓말·eli5(주석 포함), 한자·외국어·U+FFFD 금지, 원문 유지.
2. 승인·안전 6원칙(하네스 5절·파일 삭제 시 대상·이유·근거 설명)·오버레이 준수.
3. harness/HARNESS.md·AGENTS.md·dev-principles 전 항목(2~11절 전체) 선독.
4. 지정 파일 직접 수정. 임시 스크립트 금지·-c 검증.
5. 본문 도구 호출 JSON·XML 금지.
6. 실패 시 즉시 중단, 원인·상태 보고.
[작업]
- 문서: <경로> 작업 <번호>
- 참고: harness/HARNESS.md, AGENTS.md, dev-principles 경로
- 보정: 직전 <지적> / 금지 <범위>
[자기점검]
- [ ] -c 검증 통과
- [ ] dev-principles 전 항목(2~11절) 확인 1줄
- [ ] 언어 순수성·주석 eli5
- [ ] 보고: 결과1줄/불릿≤5/경로/다음1줄
`
- dev-principles 경로: .agents/skills/dev-principles/SKILL.md (Claude Code·Cursor는 .claude/skills/dev-principles/SKILL.md).
- 서브는 구현 전에 범위 안에서 같은 목적의 기존 함수·모듈이 있는지 먼저 검색해 재사용하고, 서로 다른 책임을 한 파일에 몰아넣지 않는다(폴더 안의 역할별 파일로 분리).

## 리뷰 프롬프트 (포인터 샌드위치)
리뷰 서브도 하네스 전달이 필수다. 가드레일 6줄(4번만 수정 금지) → 작업 포인터 → 자기점검 3단 구조(500자 이하)를 쓴다.
`
[가드레일]
1. 존댓말·eli5(주석 포함), 한자·외국어·U+FFFD 금지, 원문 유지.
2. 승인·안전 6원칙(하네스 5절·파일 삭제 시 대상·이유·근거 설명)·오버레이 준수.
3. harness/HARNESS.md·AGENTS.md·dev-principles 전 항목(2~11절 전체) 선독.
4. 수정 금지, 문제만 기록. 임시 스크립트 금지.
5. 본문 도구 호출 JSON·XML 금지.
6. 실패 시 즉시 중단, 원인·상태 보고.
[작업]
- 문서: <경로> 작업 <번호>
- 규격: review-harness 7항목, 하네스 7절
- 참고: harness/HARNESS.md, AGENTS.md, dev-principles 경로
- 재리뷰: 직전 지적·바뀐 파일
[자기점검]
- [ ] 검증 재실행·산출물 확인
- [ ] 주석·문서 eli5-clarity·언어 순수성
- [ ] 판정·지적(파일:라인, 심각도) 보고
`
- 판정은 critical/major 유무로만 한다. minor만 있으면 PASS다.

## 읽기 전용·기록 서브
- 읽기·기록·리서치 서브에도 개발 하네스 가드레일과 자기점검, 보고 형식을 반드시 넣어 전달한다. 하네스 생략은 금지한다. 작은 작업 여럿은 한 서브에 합친다.
- 모델은 가벼운 모델이다(하네스 8절). 리서치 서브는 표준 모델이다(plan-harness). 짧은 명령 한 줄(git status·log·diff, 커밋, 푸시, python -I -c)은 허락 후 메인이 실행한다.

## 소규모 Fast-track
- 기준: ① 단일 파일·바뀐 줄 20줄 이하(사본 동기화 제외) 단순 수정이거나, ② 하네스 설치·업데이트(정본 동기화)이며, 보안·비가역 제외(하네스 3·9절).
- 메인이 직접 처리하고 인라인 검증과 셀프 체크로 PASS를 판정한다. 서브와 리뷰 세션은 없다.
- 바뀐 줄 원문을 보고에 남긴다. VERSION은 커밋 시점에 올린다.

## 브리프 출력 (명시 요청 시에만)
- 사용자가 다른 세션·도구에 붙여 넣을 「브리프 출력」을 요청한 때만 쓴다. 파일은 만들지 않는다.
- 작업 문서 내용과 가드레일·자기점검을 합친 자체 포함 코드 블록을 채팅에 띄운다.
- 끝에 바뀐 파일 목록을 git status로 붙인다. 서브를 열지 않고 메인이 직접 조립해 출력한다.

## 보고 형식
- 정본: 결과 1줄 / 불릿 ≤5 / 경로 / 다음 1줄. 서브→메인 핸드오프도 같다.
- 실패면 원인과 파일 상태를 넣는다. 「자세히」 전에는 장문·표를 쓰지 않는다.
- 긴 툴 출력은 로그 파일에 두고 경로+한 줄 요약(+exit)만 남긴다.
- 구현 보고는 독립 리뷰 세션이 재실행으로 확인한다. Fast-track은 메인이 바뀐 줄을 읽는다.
