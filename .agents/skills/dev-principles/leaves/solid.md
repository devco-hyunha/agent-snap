# 2. SOLID

**SRP (단일 책임)**
- 정의: 파일·모듈·클래스·함수는 변경 이유가 하나여야 한다. 제품 소스 파일 하나에는 제품 책임 하나만 두고, 다른 책임은 별도 파일로 나눈다.
- 적용 범위: 제품 소스와 시험 전용 파일 모두. 「시험 파일이라 검토 대상이 아니다」는 위반이다. 시험 파일도 역할·대상별로 나눈다.
- 한곳(응집) 정본: **한곳(응집) = 같은 도메인·기능 폴더 안의 여러 단일 책임 파일. 「한곳」=「한 파일」해석은 위반. 호출처가 하나여도 책임이 둘이면 같은 폴더에 파일 둘 이상.** (`dry`·`kiss-yagni`·HARNESS는 이 문장 포인터.)
- 기준: 컴포넌트·비즈니스 로직·유틸·상수·타입이 한 파일에 섞이지 않았는지 본다. 파일이 비대하거나 역할이 여럿이면 역할별 파일로 쪼개 같은 도메인 폴더에 둔다. KISS·YAGNI·「단일 사용처」로 분리를 거부하지 않는다. 프로젝트에 더 세분 기준이 있으면 그쪽을 우선한다. 상수·사람 문구 분리 세부: `leaves/constants-locale.md`.
- 플랫폼 분기: cfg(windows)·cfg(unix) 등은 플랫폼별 파일·모듈로 나눈다(예: platform/unix.rs, platform/windows.rs). 분기가 둘 이상이면 짧아도 한 파일에 두지 않는다.
- 시험·설정: 시험 본문·검증·단정은 예외가 아니다(정본 `leaves/testing.md`). 설정 파일에는 설정만 두고 검증 코드를 넣지 않는다.
- 위반: 한 파일에 기능·헬퍼·API·상태 처리를 몰아넣는다. 「한곳에서만 쓰이니」라며 다른 책임을 동거시킨다. 주문이 가격·DB·이메일을 모두 한다. 플랫폼 분기를 한 파일에 두고 「같은 책임이라」며 분리를 거부한다.

**OCP (개방-폐쇄)**
- 정의: 확장은 기존 코드 수정 없이 가능해야 한다.
- 기준: 새 유형을 추가할 때 기존 분기문을 고쳐야 한다면 재검토한다. 변형이 실제로 둘 이상일 때만 적용한다.
- 위반: 결제 수단이 늘 때마다 거대한 if/else 체인에 분기를 추가한다.

**LSP (리스코프 치환)**
- 정의: 하위 타입은 상위 타입의 계약을 깨지 않아야 한다.
- 기준: 하위 타입을 상위 타입 자리에 넣었을 때 호출부가 타입을 따로 확인해야 하면 위반이다.
- 위반: 상위 타입의 메서드를 하위 타입이 예외로 막거나 사전조건을 강화한다.

**ISP (인터페이스 분리)**
- 정의: 쓰지 않는 메서드에 의존하지 않도록 인터페이스를 작게 나눈다.
- 기준: 구현체가 빈 메서드나 예외만 던지는 메서드를 갖고 있으면 쪼갠다.
- 위반: 읽기만 하는 소비자가 쓰기, 삭제 메서드까지 가진 인터페이스를 받는다.

**DIP (의존 역전)**
- 정의: 고수준 모듈은 구체 구현이 아니라 추상에 의존한다.
- 기준: 비즈니스 로직이 DB 클라이언트나 HTTP 라이브러리를 직접 생성하면 주입으로 바꾼다.
- 위반: 서비스 함수 안에서 특정 DB 드라이버를 직접 import해 연결한다.
