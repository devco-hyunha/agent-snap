# 기획·개발 하네스 설계 기록

- 문서 성격: 사람이 나중에 읽고 판단하기 위한 설계 기록
- 상태: 운영 중. 확정되지 않은 항목은 10절에 모았다.
- 위치: 이 저장소의 harness/HARNESS.md가 정본이다. 적용받는 프로젝트에는 PROJ/harness/HARNESS.md에 둔다.

## 1. 목적과 범위

- 목적: 기획과 개발을 한 흐름으로 돕는 하네스. 요구 수렴부터 구현, 리뷰, 상태 갱신까지 같은 절차로 진행한다. 특정 AI 도구에 묶이지 않고 여러 도구가 함께 쓴다.
- 범위: 스킬과 핵심 규칙 블록. 복사해 둔 위치에 따라 적용 범위가 정해진다.
- 우선순위: 아래 "언어와 우선순위"를 따른다. 이 하네스는 프로젝트 규칙이 비어 있는 부분만 채운다.

### 언어와 우선순위

- 응답 언어는 사용자가 쓰는 언어를 따른다. 사용자에게 보내는 모든 문장(진행 상황, 설명, 보고, 질문), 서브에이전트(하위 에이전트)에 보내는 지시와 보고, 작성하는 문서, 코드 주석과 커밋 메시지, 대화에 같은 원칙을 적용한다. 존중하는 공손 어투(존댓말)를 유지한다. 반말과 무례한 말투는 쓰지 않는다.
- 한자·외국어 서술을 섞지 않는다. 깨진 글자(U+FFFD)를 쓰지 않는다. 로컬 양자화 모델에서 자주 나는 혼입을 막기 위한 규칙이다.
- 설명·보고와 코드 주석·독스트링에는 쉬운 설명 규칙(eli5-clarity)을 항상 적용한다. 코드 주석은 코드로 드러나지 않는 의도·이유·근거를 결론 먼저 1~2문장으로 쓰고, 외국어·한자를 섞지 않는다. 결론을 앞에 두고, 군더더기·AI식 완곡을 줄이며, 짧은 문장으로 한 포인트씩 쓴다. 전문 용어는 첫 등장에 짧게 풀이한다. 비유는 개념이 어려울 때만 최대 하나. 사람 기준으로 쓰고, 보안·비가역 안내는 예외로 또렷하게 쓴 뒤 돌아온다. 정본: .agents/skills/eli5-clarity/SKILL.md (Claude Code·Cursor는 .claude/skills/eli5-clarity/SKILL.md).
- 코드, 경로, 명령, 식별자, 인용은 원문 그대로 둔다. 번역하거나 바꾸지 않는다.
- 프로젝트 규칙(AGENTS.md, CLAUDE.md, GEMINI.md, docs/ 등)이 있으면 우선한다. 단, 승인·안전 규칙(이 하네스 5절의 승인·안전 규칙 전체)은 이 하네스가 우선한다. 충돌 해소 기준은 아래 "베이스 하네스와 프로젝트 오버레이"와 5절을 따른다.

### 베이스 하네스와 프로젝트 오버레이

결론: 하네스는 읽기 전용 베이스이고, 프로젝트 고유 규칙은 정해진 한 곳(오버레이)에만 둔다. 그러면 하네스를 업데이트해도 고유 규칙이 남는다.

- 마커 불변: `<!-- agent-harness:begin -->`~`<!-- agent-harness:end -->` 구간과 harness/HARNESS.md는 소비 프로젝트(하네스를 가져다 쓰는 프로젝트)에서 직접 고치지 않는다. 업데이트 때 통째로 교체한다.
- 단일 슬롯: 프로젝트 고유 규칙과 예외는 AGENTS.md의 마커 바깥 `## 프로젝트 오버레이` 절 한 곳에만 둔다. 분량이 크면 docs/PROJECT_RULES.md를 가리키는 링크 한 줄만 둔다.
- 안전 규칙 충돌: 승인·안전 규칙보다 더 엄격한 오버레이(예: 커밋 전면 금지, 특정 언어 고정)는 자동으로 우선한다. 완화하는 오버레이(예: 조건부 자동 커밋)는 오버레이 절에 `[안전 예외 승인: N번]`(N은 5절 번호)을 명시한 때만 허용한다. 선언이 없으면 5절이 이긴다.
- 버전과 줄바꿈: 소비 프로젝트에 저장소 루트의 VERSION을 harness/VERSION으로 복사해 어느 버전인지 추적한다. 이 저장소의 .gitattributes(`* text=auto eol=lf`)를 함께 두어 줄바꿈(CRLF/LF) 차이로 생기는 가짜 변경을 막는다.

### 사용자 대화(게이트 대화)

- 메인이 사용자에게 상세히 말하는 때는 승인 요청, 결론을 바꾸는 질문(최대 3개), 멈춤 조건 보고, 작업 완료 보고다. 중간 진행은 한 줄 이하이거나 생략한다. 상세는 작업 문서와 로그 경로로 돌린다. 사용자가 「자세히」를 요청하면 상한을 잠시 해제한다.

스킬 정본은 이 저장소의 skills/<이름>/SKILL.md다. 소비 프로젝트에는 도구별 경로로 복사하고, 이 저장소는 skills/, .agents/skills/, .claude/skills/ 3벌을 바이트 동일하게 유지한다. 4대 주력 도구의 규칙·스킬 경로는 아래 표이며, README의 지원 표는 이 표를 따른다. 하네스 문서 위치는 프로젝트의 harness/HARNESS.md다.

|---|---|---|---|
| Claude Code | CLAUDE.md(`@AGENTS.md` 연결) | .claude/skills | 서브에이전트를 열 수 있고 모델 단계를 지정한다. |

| Codex | AGENTS.md | .agents/skills | 도구가 지원하는 방식을 쓰며, 없으면 아래 "서브에이전트가 없는 도구" 절차를 따른다. |

서브에이전트 지원과 모델 지정은 도구와 버전마다 다르다. 열기 전 호출 도구의 schema로 확인한다(3절). 그 밖의 도구(Gemini CLI, Antigravity, GitHub Copilot)는 README 지원 표를 따른다.

운영 규칙: 스킬 파일은 80줄 이하, 3,500자 이하를 지킨다. 단, dev-principles는 원칙 항목이 많아 두 상한 모두 예외로 둔다.

## 3. 흐름

1. 규칙·오버레이 확인: AGENTS.md의 `## 프로젝트 오버레이`, docs/PROJECT_RULES.md, docs/INDEX.md를 읽는다.
2. 조건부 리서치(Research Gate): 아래 "조건부 논문·기술 리서치" 조건에 해당할 때만 한다.
3. 요구 수렴: 사용자의 목표, 제약, 완료 조건을 정리한다.
4. 작업 문서 작성: 기획용 작업 문서 하나에 작업 목록, 경계, 완료 기준, 검증 방법, 작업별 범위·금지 사항·산출물·검증 명령을 쓴다.
5. 사용자 승인: 작업 문서를 사용자가 승인한다. (5절 1번)
6. 작업별 구현(서브에이전트 위임): 작업마다 새 구현 서브에이전트에 위임한다. 구현 서브는 구현, 인라인 검증, 함수 중복(DRY) 자기 확인까지 한다.
7. 독립 리뷰 세션: 서브의 보고를 믿지 않는다. 구현 맥락이 없는 새 읽기 전용 세션이 검증 명령 재실행, 산출물 실재 확인, 7대 체크리스트 리뷰, DRY 확인을 한 번에 한다. 기존 '확인 전용 서브'는 이 단계에 합쳐 3단계를 2단계(구현 서브, 독립 리뷰 세션)로 줄였다.
8. 보정과 재리뷰: 지적을 고치고 다시 리뷰한다. 범위는 9절을 따른다.
9. 상태 갱신: 작업 문서를 현재 상태로 갱신한다.
10. 커밋: 작업 단위 전체 리뷰가 PASS한 뒤 사용자 허락을 받아 한다. 5절 3번을 따른다.

### 조건부 논문·기술 리서치 (Research Gate)

- 실행 조건(하나라도 해당하면 한다): ① 사용자가 논문·리서치·벤치마크 조사를 요청했다. ② 알고리즘·AI/ML·양자화·오디오/영상·성능·아키텍처 선정처럼 학술·기술 근거가 설계 결론을 바꾼다. ③ 프로젝트 오버레이(AGENTS.md 또는 docs/PROJECT_RULES.md)에 `[기획 리서치: 필수]`가 선언되어 있다.
- 생략: 단순 기능 수정·UI·문서 작업은 하지 않는다. 토큰을 아끼기 위해서다.
- 방식: 메인이 직접 검색하지 않는다. 읽기 전용 리서치 서브에이전트(표준 모델)에 논문·공식 문서·벤치마크 조사를 맡긴다. 서브는 출처 링크, 핵심 수치·교훈, 채택·기각 근거만 짧게 보고한다.
- 기록: 메인이 보고를 정리해 기획 작업 문서의 `## 리서치 및 설계 근거`(조건부 필수) 절에 남긴다. 조건에 해당하면 이 절이 있어야 승인을 요청한다.

### 세션별 역할 (공통·부모·자식)

- 공통(메인·구현 서브·리뷰 서브 전원): 1절 언어 규칙(코드 주석·독스트링의 eli5-clarity 포함), 오버레이 규칙, 5절 승인·안전 6원칙을 하나도 빠뜨리지 않고 따른다.
- 부모(메인): 기획 수렴, 승인 요청, 작업 문서 결정, 위임 지시, 최종 보고만 한다. 아래 "위임 규칙"을 따른다.
- 자식(구현·보정 서브): 지정된 작업 문서와 대상 파일만 읽고 바로 수정한다. dev-principles 2~10절과 코드 주석 eli5-clarity를 지키고, 인라인(-c) 검증과 DRY·에러 처리·보안 자기확인 결과를 보고한다.
- 자식(독립 리뷰 서브): 구현 맥락이 없는 새 읽기 전용 세션이다. 검증 재실행, 산출물 확인, 7대 체크리스트(코드 주석 eli5-clarity·언어 순수성 포함), DRY 확인을 하고 판정한다(7절).
- 서브는 대화 맥락이 없다. 하네스는 아래 포인터 샌드위치 프롬프트로 주입한다.

### 소규모 Fast-track

- 조건: ① 단일 파일·바뀐 줄 20줄 이하(사본 동기화 제외)의 단순 수정이거나, ② 하네스 설치·업데이트(정본 파일 복사·마커 블록 교체·오버레이 보존 정리·인라인 해시 검증)이며, 보안·비가역 작업이 아니다.
- 절차: 서브에이전트를 열지 않고 메인이 직접 수행하며, 인라인 검증과 셀프 체크(AC·금지 사항·범위 밖 변경·DRY·해시 일치)를 한 뒤 메인이 PASS를 판정한다(5절 5번).
- 조건을 하나라도 벗어나거나 사용자가 리뷰를 요청하면 표준 2단계를 따른다. 기준은 9절이다.

### 위임 규칙

- 위임 범위: 파일 읽기·검색·수정·쓰기·상태 갱신·작업 문서 기록·리뷰 실행은 서브에이전트나 리뷰 세션이 맡는다. 짧은 명령 한 줄 실행(git status·log·diff, 커밋, 푸시, python -c 인라인 검증)는 허락을 받아 메인이 직접 실행한다. 커밋·푸시는 사용자 허락이 필요하다. 메인은 승인 대화, 작업 문서 내용 결정, 지시 작성, 결과 확인, 사용자 보고만 한다. 단, 메인은 판단 규칙 확인을 위해 이 하네스의 기록 문서와 스킬 파일(SKILL.md)은 직접 읽을 수 있다. 파일 읽기·검색 잡음이 부모에 남는 것을 피하는 것이 서브 위임의 목적이다.
- 열기 전 도구 확인: 서브에이전트를 열기 전에 호출 도구의 schema를 읽어서 도구 이름, 매개변수, 서브에이전트 종류 지정 방법, 모델 지정 방법을 확인하고 schema대로 호출한다. 추측으로 호출하지 않고, 호출 실패 시 schema를 다시 읽어 호출 구조를 고친다.
- 모델 지정: 서브에이전트를 띄울 때마다 모델 단계를 지정한다(8절). 사용자에게 묻지 않고 작업에 맞게 스스로 고른다.
- 개발 규칙 명시: 구현·보정 위임 프롬프트의 가드레일에 dev-principles 2~10절(SOLID, 관심사 분리, 에러 처리, 보안 기본, 이름과 함수, 코드 주석 eli5-clarity)과 프로젝트 규칙(AGENTS.md)을 먼저 읽으라고 적고, 참고 줄에 두 경로를 둔다.
- 중복 확인: 구현·보정 위임은 구현 후 같은 목적의 함수가 중복되지 않았는지(자기 확인으로 dev-principles 3절 DRY, 6절 이름과 함수) 확인하고 그 결과를 보고에 남긴다. 독립 리뷰 세션도 함수 중복을 함께 확인한다.
- 포인터 샌드위치 주입: 하네스는 서브에이전트에 자동 주입되지 않고, 긴 프롬프트 중간에서는 희석된다. 그래서 위임 프롬프트는 [맨 앞: 가드레일 6줄] → [중간: 작업 문서 절대 경로·작업 번호·참고 경로(보정이면 직전 미달 지적·변경 금지 범위)] → [맨 끝: 자기점검 4줄]로만 쓰고 총 500자 이하로 둔다. 작업 문서 본문은 프롬프트에 다시 적지 않는다. 정본 문안은 delegation-brief다.
- 자체 포함 프롬프트 예외: 사용자가 다른 세션·도구에 붙여 넣을 「브리프 출력」을 명시적으로 요청한 때만 작업 문서 내용을 합친 코드 블록을 채팅에 출력한다.
- 핸드오프: 서브→메인 보고는 판정·AC 요약·산출물 경로 중심이다. 장문 본문을 부모 채팅에 다시 붙여 넣지 않는다. 보고 형식 정본은 delegation-brief다.
- 실패 처리(기존 서브에이전트를 이어 쓰지 않고 새로 열기): build-harness 스킬의 "실패 처리" 절을 따른다.
- 진행 표시: 터미널 명령은 진행이 보이게 한다. 오래 걸리는 명령은 단계마다 echo를 남기고, 테스트는 진행률이 로그에 남는 옵션을 쓴다. 긴 툴 출력은 파일(로그)에 두고 컨텍스트·보고에는 경로·한 줄 요약·exit code만 남긴다. 로그 위치는 프로젝트 관례가 있으면 그것을 쓰고, 없으면 작업 문서에 경로를 명시한다(예: `.local/`). 비밀 값과 .env는 로그에 넣지 않는다. 같은 계열 반복 Shell·실험은 가능하면 한 스크립트·한 로그로 묶는다. Await·폴링은 남발하지 않고 로그 꼬리·완료 통지만 쓴다. 로그 경로를 사용자에게 알린다.

### 서브에이전트가 없는 도구

서브에이전트를 쓸 수 없는 도구에서는 같은 절차를 대체 방식으로 진행한다.

- 메인이 같은 절차(1~10단계)를 단계별로 직접 진행한다.
- 위임 대신 단계마다 작업 문서를 갱신해, 맥락이 끊겨도 문서만으로 이어 갈 수 있게 한다.
- 리뷰는 구현 맥락이 없는 새 대화(세션)에서 한다. 새 대화에는 작업 문서, 체크리스트, 판정 기준만 전달한다.
- 검증 명령은 새 대화(리뷰)가 직접 다시 실행해 확인한다. 실행할 수 없으면 메인이 다시 실행한다.
- 새 대화에서의 리뷰는 사용자에게 새 대화를 열어 리뷰를 요청해 달라고 안내한다.
- 승인·안전 규칙(5절)과 진행 표시 규칙은 그대로 적용한다.

## 4. 승인 게이트

규칙은 5절 "승인·안전 규칙"을 따른다. 이 절은 승인 단계의 흐름만 적는다.

- 기획 단계: 리서치 조건(3절)에 해당하면 `## 리서치 및 설계 근거`를 채운 뒤 승인을 요청한다. 사용자가 작업 문서를 승인하면 구현에 들어간다.
- 구현 단계: 5절 2번의 멈추는 조건이 아니면 승인을 다시 묻지 않고 이어 간다.
- 리뷰 단계: PASS 또는 미달은 독립 리뷰 세션이 판정한다. 소규모 Fast-track만 메인 셀프 체크로 판정한다.
- 커밋 단계: 사용자가 허락하면 커밋한다.

## 5. 승인·안전 규칙

1. 기획 승인 전에는 코드를 쓰지 않는다.
2. 구현 중에는 멈추지 않는다. 멈추는 조건은 다음 다섯 가지뿐이다.
   - 새 권한이 필요할 때
   - 비가역 작업일 때
   - 보안에 관련될 때
   - 제품 결과를 바꿔야 할 때
   - 같은 지적으로 보정을 2회 한 뒤에도 미달일 때
3. 커밋, 푸시, 병합은 사용자가 허락해야 한다. (오버레이에 `[안전 예외 승인: 3번]`이 명시된 경우만 예외다.)
4. 비밀 값과 .env는 커밋하지 않는다. 로그에도 남기지 않는다.
5. 리뷰 없이 PASS 처리하지 않는다. 표준 작업의 판정은 독립 리뷰 세션이 하고, 소규모 Fast-track(3절, 9절)은 메인 셀프 체크가 한다.

6. 요청받지 않은 코드를 생성하지 않는다.
   - 지시되지 않은 파일은 만들지 않는다. 검증은 임시 스크립트 파일(_verify*.py 등)을 만들지 않고 인라인(-c)으로 실행한다.
   - 문서의 코드 샘플은 사용자가 요청한 때만 담고 간결하게 유지한다. 본보기를 이유로 긴 코드를 넣지 않는다.

### 프로젝트 오버레이와의 충돌 해소

- 더 엄격한 방향(예: AI 커밋 전면 금지, 미확정 결정 시 멈춤 추가, 특정 언어 고정)은 프로젝트 오버레이가 자동으로 우선한다.
- 완화하는 방향(예: 리뷰 PASS 시 조건부 자동 커밋)은 오버레이 절에 `[안전 예외 승인: N번]`을 명시한 때만 허용한다. 선언이 없으면 위 6원칙이 이긴다.
- 오버레이 위치와 마커 불변 원칙은 1절을 따른다.

## 6. 요청 규격 (delegation-brief)

### 전달 경로

결론: 작업 문서는 기획용 하나(`docs/tasks/<순번>-<작업명>.md`)로 단일화하고, 프롬프트는 그 문서를 가리키는 포인터만 보낸다. 같은 내용을 문서·프롬프트·별도 brief로 세 번 적던 중복을 없앴다.

- 단일 작업 문서: 작업별 범위·금지 사항·산출물·검증 명령을 기획용 작업 문서의 각 작업 절에 쓴다. 별도 `brief-N.md`는 만들지 않는다. 필드의 정본은 plan-harness 스킬이다.
- 이력 보존: 과거 brief 파일은 지우지 않고 docs/INDEX.md와 16-harness-rebalancing.brief-01~03.md에 '단일 작업 문서 체제로 통합됨'을 표시한다.
- 포인터 샌드위치 프롬프트(500자 이하)의 정본 문안, 읽기 전용 서브 프롬프트, 리뷰 프롬프트, 브리프 출력 규칙은 delegation-brief 스킬이다.
- 구현 서브도 검증 명령을 실행해 보고하고, 독립 리뷰 세션이 다시 실행해 확인한다.

### 하네스 주입

하네스 사본은 프롬프트의 맨 앞(가드레일 6줄)과 맨 끝(자기점검 4줄)에만 주입한다. 작업 문서 파일에는 사본을 기록하지 않는다(3절 포인터 샌드위치 주입).

## 7. 리뷰 규격

- 새 세션: 구현 맥락을 가진 세션이 아니라 새 세션에서 리뷰한다.
- 새 세션은 구현 맥락이 없는 새 읽기 전용 서브에이전트를 뜻한다. 서브에이전트가 없는 도구에서는 새 대화를 뜻한다. 메인은 포인터 샌드위치 프롬프트(delegation-brief)로 작업 문서 경로·작업 번호·직전 지적을 보내고, 리뷰어는 review-harness 체크리스트 7항목과 이 절의 판정 기준을 직접 읽는다. 참고 줄에는 도구별 스킬 위치(README 지원 표)의 dev-principles 경로를 넣는다(.agents/skills/dev-principles/SKILL.md, Claude Code와 Cursor는 .claude/skills/dev-principles/SKILL.md). 리뷰어는 dev-principles 2~10절과 함수 중복(DRY)을 함께 확인한다.
- 읽기 전용: 리뷰어는 파일을 수정하지 않는다. 판정은 리뷰 세션이 한다(5절 5번).
- 통합 확인: 독립 리뷰 세션이 검증 명령을 다시 실행해 결과를 확인하고, 산출물이 실제로 있는지 확인한 뒤 체크리스트를 본다. 별도의 확인 전용 서브는 열지 않는다. 절차는 3절을 따른다.
- 체크리스트 7항목의 정본은 review-harness 스킬이다.
- 심각도 기준
  - critical: 반드시 고쳐야 하는 것. 보안, 데이터 손실, 요구 위반은 항상 critical로 본다.
  - major: 동작 오류나 완료 기준 미달.
  - minor: 스타일, 명명, 개선 제안. 보정 대상에서 걸러 낼 수 있다.
- 판정은 critical/major 유무로만 한다. minor만 있으면 PASS다.
- 리뷰에서 보안 관련 critical이 나오면 5절 2번에 따라 멈추고 사용자에게 보고한다.
- 리뷰 범위: 9절 참조.

## 8. 모델 선택

서브에이전트에 지정하는 모델은 세 단계로 나눈다.

- 가벼운 모델: 단순 작업(파일 찾기, 로그 확인, 결과 정리)
- 표준 모델: 구현·디버깅·일반 설계 판단
- 가장 강한 모델: 어려운 설계 판단에 쓸 수 있다.

서브에이전트를 띄울 때마다 단계를 지정하고, 사용자에게 묻지 않고 난이도로 고른다. 서브에이전트에 모델을 지정할 수 없는 도구는 기본 모델을 쓴다.

| 단계 | Claude Code 예시 | 그 밖의 도구 |
|---|---|---|
| 가벼운 모델 | haiku | 각 도구의 가벼운 모델 |
| 표준 모델 | sonnet | 각 도구의 표준 모델 |
| 가장 강한 모델 | opus | 각 도구의 상위 모델 |

## 9. 리뷰 범위 규칙

- 표준 작업은 크기로 나누지 않는다. 모두 구현 서브, 독립 리뷰 세션의 2단계를 따르고, 리뷰 범위를 정할 때도 크기를 쓰지 않는다.
- 유일한 예외는 소규모 Fast-track이다. 조건은 ① 단일 파일·바뀐 줄 20줄 이하(사본 동기화 제외)의 단순 수정이거나, ② 하네스 설치·업데이트(정본 동기화)이며 보안·비가역 작업이 아닐 때다. 이때 서브나 별도 리뷰 세션을 열지 않고 메인이 직접 수행해 인라인 검증과 셀프 체크로 PASS를 판정한다. 조건을 하나라도 벗어나면 표준으로 돌아간다. 스킬이 다른 기준(예: 10줄)을 적고 있으면 이 절이 우선하며, 스킬은 이 절에 맞춘다.
- 용어: 판정(PASS/미달)은 리뷰 1회의 결과다. 체크리스트 항목별 결과는 '통과 항목'과 '미달 항목'으로 부른다.
- 재리뷰는 직전 리뷰 이후 변경분과 직전 리뷰의 미달 항목만 본다. 직전 리뷰의 통과 항목은 다시 보지 않는다. 작업 단위가 끝나면 작업 전체를 한 번 리뷰한다.

## 10. 미결정·결정 사항

- 미결정: Antigravity 전역 규칙 경로와 Copilot CLI 경로는 공식 문서로 확인하지 못해 안내에서 제외한다.

### 결정 사항

- 기록 위치: 이 저장소가 정본이며, 다른 곳에서 쓸 때는 필요한 파일을 복사해 쓴다.
- 파일 단위 단일 책임·테스트 배치(언어 비종속 공통 규칙): 제품 소스 파일 하나에는 제품 책임만 하나 둔다. 테스트 본문은 제품 소스 파일에 두지 않으며, 「함께」는 같은 변경 세트·같은 검토 단위·가까운 디렉터리(같은 파일 동거 아님)이다. 상세 정본은 `dev-principles`, 리뷰 점검은 `review-harness`다. 프로젝트 규칙 우선(1절)·승인·안전(5절)과 충돌하지 않는다. 신규 동거·책임 혼재 확대는 major, 레거시만이면 minor+이전 메모.
