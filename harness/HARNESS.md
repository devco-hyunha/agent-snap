# 기획·개발 하네스 설계 기록

- 문서 성격: 사람이 나중에 읽고 판단하기 위한 설계 기록
- 상태: 운영 중. 확정되지 않은 항목은 10절에 모았다.
- 위치: 이 저장소의 harness/HARNESS.md가 정본이다. 적용받는 프로젝트에는 PROJ/harness/HARNESS.md에 둔다.

## 1. 목적과 범위

- 목적: 기획과 개발을 한 흐름으로 돕는 하네스. 요구 수렴부터 구현, 리뷰, 상태 갱신까지 같은 절차로 진행한다. 특정 AI 도구에 묶이지 않고 여러 도구가 함께 쓴다.
- 범위: 스킬과 핵심 규칙 블록. 복사해 둔 위치에 따라 적용 범위가 정해진다.
- 우선순위: 아래 "언어와 우선순위"를 따른다. 이 하네스는 프로젝트 규칙이 비어 있는 부분만 채운다.

### 언어와 우선순위

- 응답 언어는 사용자가 쓰는 언어를 따른다. 사용자에게 보내는 모든 문장(진행 상황, 설명, 보고, 질문), 서브에이전트(하위 에이전트)에 보내는 지시와 보고, 작성하는 문서, 코드 주석과 커밋 메시지, 대화에 같은 원칙을 적용한다. 정중한 존댓말을 유지한다.
- 코드, 경로, 명령, 식별자, 인용은 원문 그대로 둔다. 번역하거나 바꾸지 않는다.
- 프로젝트 규칙(AGENTS.md, CLAUDE.md, GEMINI.md, docs/ 등)이 있으면 우선한다. 단, 승인·안전 규칙(이 하네스 5절의 승인·안전 규칙 전체)은 이 하네스가 우선한다.

## 2. 구성 요소

| 구성 요소 | 경로 | 역할 |
|---|---|---|
| plan-harness | .agents/skills/plan-harness/SKILL.md | 요구를 수렴하고 작업 문서를 작성해 사용자 승인까지 이끈다. |
| build-harness | .agents/skills/build-harness/SKILL.md | 승인된 작업 문서를 작업별로 서브에이전트에 위임해 구현하고 확인 전용 서브에이전트가 결과를 확인하고 메인이 판단한다. |
| review-harness | .agents/skills/review-harness/SKILL.md | 새 세션에서 읽기 전용으로 리뷰하고 보정 후 재리뷰한다(범위는 9절). |
| delegation-brief | .agents/skills/delegation-brief/SKILL.md | 서브에이전트에게 줄 요청(작업 문서 + 자체 포함 프롬프트)의 규격을 정한다. |
| dev-principles | .agents/skills/dev-principles/SKILL.md | 개발 전반에 적용하는 공통 원칙을 제공한다. |
| proofread-harness | .agents/skills/proofread-harness/SKILL.md | 한국어 문서와 보고 문장을 제안, 승인, 적용 순서로 교정한다. |
| 핵심 규칙 블록 | templates/AGENTS.harness.md | 핵심 규칙 블록이 기본 전달 수단이다. |

스킬 경로는 프로젝트의 .agents/skills/<이름>/SKILL.md를 기본으로 쓴다. Claude Code는 .claude/skills/<이름>/SKILL.md를 쓴다. 도구별 위치는 이 절을 따른다. README의 지원 표는 이 절을 따른다. 하네스 문서 위치는 프로젝트의 harness/HARNESS.md다.

운영 규칙: 스킬 파일은 80줄 이하를 목표로 한다. 단, dev-principles는 원칙 항목이 많아 예외로 둔다.

## 3. 흐름

1. 요구 수렴: 사용자의 목표, 제약, 완료 조건을 정리한다.
2. 작업 문서 작성: 작업 목록, 경계, 완료 기준, 검증 방법을 문서로 쓴다.
3. 사용자 승인: 작업 문서를 사용자가 승인한다. (5절 1번)
4. 작업별 구현(서브에이전트 위임): 작업마다 새 서브에이전트에 위임한다.
5. 결과 확인: 서브에이전트의 보고를 믿지 않고 확인 전용 서브에이전트가 결과를 직접 확인한다.
6. 새 세션 리뷰: 구현 맥락이 없는 새 세션이 읽기 전용으로 리뷰한다.
7. 보정과 재리뷰: 지적을 고치고 다시 리뷰한다. 범위는 9절을 따른다.
8. 상태 갱신: 작업 문서를 현재 상태로 갱신한다.
9. 커밋: 작업 단위 전체 리뷰가 PASS한 뒤 사용자 허락을 받아 한다. 5절 3번을 따른다.

### 위임 규칙

- 위임 범위: 파일 읽기·검색·수정·쓰기·상태 갱신·작업 문서 기록·리뷰 실행은 서브에이전트나 리뷰 세션이 맡는다. 짧은 명령 한 줄 실행(git status·log·diff, 커밋, 푸시, python -c 인라인 검증)는 허락을 받아 메인이 직접 실행한다. 커밋·푸시는 사용자 허락이 필요하다. 메인은 승인 대화, 작업 문서 내용 결정, 지시 작성, 결과 확인, 사용자 보고만 한다. 단, 메인은 판단 규칙 확인을 위해 이 하네스의 기록 문서와 스킬 파일(SKILL.md)은 직접 읽을 수 있다. 파일 읽기·검색 잡음이 부모에 남는 것을 피하는 것이 서브 위임의 목적이다.
- 열기 전 도구 확인: 서브에이전트를 열기 전에 호출 도구의 schema를 읽어서 도구 이름, 매개변수, 서브에이전트 종류 지정 방법, 모델 지정 방법을 확인하고 schema대로 호출한다. 추측으로 호출하지 않고, 호출 실패 시 schema를 다시 읽어 호출 구조를 고친다.
- 모델 지정: 서브에이전트를 띄울 때마다 모델 단계를 지정한다(8절). 사용자에게 묻지 않고 작업에 맞게 스스로 고른다.
- 개발 규칙 명시: 구현·보정 위임을 열 때 프롬프트에 프로젝트 규칙 문서 경로와 dev-principles 스킬 경로를 담고, 적용 항목(SOLID, 관심사 분리, 에러 처리, 보안 기본, 이름과 함수)을 함께 적는다. 프로젝트 개발 규칙(AGENTS.md 개발 규칙 절)과 dev-principles 2~10절이 기본이다.
- 중복 확인: 구현·보정 위임은 구현 후 같은 목적의 함수가 중복되지 않았는지(자기 확인으로 dev-principles 3절 DRY, 6절 이름과 함수) 확인하고 그 결과를 보고에 남긴다. 확인 전용 위임과 리뷰 세션도 함수 중복을 함께 확인한다.
- 하네스 주입: 구현·보정 위임 프롬프트에는 하네스 핵심 규칙 사본(원문 유지, 프로젝트 규칙 우선, 승인·안전, 검증 인라인(-c), 개발 원칙 적용 항목, 중복 확인)과 dev-principles·프로젝트 개발 규칙 경로를 원문 그대로 담는다. 정본 문안은 delegation-brief 스킬의 '하네스 주입 사본' 절이다.
- 실패 처리(기존 서브에이전트를 이어 쓰지 않고 새로 열기): build-harness 스킬의 "실패 처리" 절을 따른다.
- 진행 표시: 터미널 명령은 진행 상황이 보이도록 한다. 오래 걸리는 명령은 단계마다 echo로 표시를 남기고, 테스트는 -v나 진행률이 로그에 남는 옵션을 쓴다. 로그 파일 경로를 사용자에게 알린다.

### 서브에이전트가 없는 도구

서브에이전트를 쓸 수 없는 도구에서는 같은 절차를 대체 방식으로 진행한다.

- 메인이 같은 절차(1~9단계)를 단계별로 직접 진행한다.
- 위임 대신 단계마다 작업 문서를 갱신해, 맥락이 끊겨도 문서만으로 이어 갈 수 있게 한다.
- 리뷰는 구현 맥락이 없는 새 대화(세션)에서 한다. 새 대화에는 작업 문서, 체크리스트, 판정 기준만 전달한다.
- 확인 단계는 메인이 검증 명령을 직접 다시 실행해 확인한다.
- 새 대화에서의 리뷰는 사용자에게 새 대화를 열어 리뷰를 요청해 달라고 안내한다.
- 승인·안전 규칙(5절)과 진행 표시 규칙은 그대로 적용한다.

## 4. 승인 게이트

규칙은 5절 "승인·안전 규칙"을 따른다. 이 절은 승인 단계의 흐름만 적는다.

- 기획 단계: 사용자가 작업 문서를 승인하면 구현에 들어간다.
- 구현 단계: 5절 2번의 멈추는 조건이 아니면 승인을 다시 묻지 않고 이어 간다.
- 리뷰 단계: PASS 또는 미달은 리뷰 세션이 판정한다.
- 커밋 단계: 사용자가 허락하면 커밋한다.

## 5. 승인·안전 규칙

1. 기획 승인 전에는 코드를 쓰지 않는다.
2. 구현 중에는 멈추지 않는다. 멈추는 조건은 다음 다섯 가지뿐이다.
   - 새 권한이 필요할 때
   - 비가역 작업일 때
   - 보안에 관련될 때
   - 제품 결과를 바꿔야 할 때
   - 같은 지적으로 보정을 2회 한 뒤에도 미달일 때
3. 커밋, 푸시, 병합은 사용자가 허락해야 한다.
4. 비밀 값과 .env는 커밋하지 않는다.
5. 리뷰 없이 PASS 처리하지 않는다. 리뷰 판정은 리뷰 세션이 한다.

6. 요청받지 않은 코드를 생성하지 않는다.
   - 지시되지 않은 파일은 만들지 않는다. 검증은 임시 스크립트 파일(_verify*.py 등)을 만들지 않고 인라인(-c)으로 실행한다.
   - 문서의 코드 샘플은 사용자가 요청한 때만 담고 간결하게 유지한다. 본보기를 이유로 긴 코드를 넣지 않는다.

## 6. 요청 규격 (delegation-brief)

### 전달 경로

구현·보정 위임은 작업 문서와 자체 포함 프롬프트, 두 경로로 함께 전달한다. 한쪽이 빠져도 서브에이전트가 일을 이어 갈 수 있게 하기 위함이다. 작업 문서 필수 여부는 delegation-brief를 따른다.

### 작업 문서 두 종류

기획용 작업 문서와 위임용 작업 문서는 서로 다르다. 위임용 작업 문서는 승인된 기획용 작업 문서를 바탕으로 만든다.

- 기획용 작업 문서 필드의 정본은 plan-harness 스킬이다.
- 위임용 작업 문서(delegation-brief): 필수 섹션(서브에이전트 보고에서 채택한 근거(출처 포함) 포함)과 보정 작업 추가 항목은 delegation-brief 스킬이 정본이다.

### 자체 포함 프롬프트 항목

항목 정본은 delegation-brief 스킬이다.

### 공통 지시 6개

공통 지시 6개의 정본은 delegation-brief 스킬이다.

첫 동작 규칙의 정본은 delegation-brief 공통 지시 1번이다.

금지 사항 섹션 내용은 delegation-brief를 따른다. 구현 서브에이전트도 검증 명령을 실행해 보고하고, 확인 전용 서브에이전트가 다시 실행해 확인한다.

### 하네스 주입

하네스 주입 사본의 정본은 delegation-brief 스킬이다. 구현·보정 위임 프롬프트에는 사본 6항목과 dev-principles·프로젝트 개발 규칙 경로를 담고, 위임용 작업 문서의 '하네스 주입(사본)' 섹션과 같은 문안으로 둔다.

## 7. 리뷰 규격

- 새 세션: 구현 맥락을 가진 세션이 아니라 새 세션에서 리뷰한다.
- 새 세션은 구현 맥락이 없는 새 읽기 전용 서브에이전트를 뜻한다. 서브에이전트가 없는 도구에서는 새 대화를 뜻한다. 메인은 review-harness 체크리스트 6항목과 7절 판정 기준을 리뷰 프롬프트에 담아 보낸다. 리뷰 프롬프트에는 도구별 스킬 위치(README 지원 표)의 dev-principles 경로를 명시해 넣는다(.agents/skills/dev-principles/SKILL.md, Claude Code와 Cursor는 .claude/skills/dev-principles/SKILL.md). 리뷰 프롬프트에는 dev-principles 2~10절 항목과 함수 중복(DRY) 확인을 함께 담는다.
- 읽기 전용: 리뷰어는 파일을 수정하지 않는다. 판정은 리뷰 세션이 한다(5절 5번). 확인 절차는 3절을 따른다.
- 체크리스트 6항목의 정본은 review-harness 스킬이다.
- 심각도 기준
  - critical: 반드시 고쳐야 하는 것. 보안, 데이터 손실, 요구 위반은 항상 critical로 본다.
  - major: 동작 오류나 완료 기준 미달.
  - minor: 스타일, 명명, 개선 제안. 보정 대상에서 걸러 낼 수 있다.
- 판정은 critical/major 유무로만 한다. minor만 있으면 PASS다.
- 리뷰에서 보안 관련 critical이 나오면 5절 2번에 따라 멈추고 사용자에게 보고한다.
- 리뷰 범위: 9절 참조.

## 8. 모델 선택

서브에이전트에 지정하는 모델은 세 단계로 나눈다.

- 가벼운 모델: 단순 작업(파일 찾기, 로그 확인, 결과 정리)
- 표준 모델: 구현·디버깅·일반 설계 판단
- 가장 강한 모델: 어려운 설계 판단에 쓸 수 있다.

서브에이전트를 띄울 때마다 단계를 지정하고, 사용자에게 묻지 않고 난이도로 고른다. 서브에이전트에 모델을 지정할 수 없는 도구는 기본 모델을 쓴다.

| 단계 | Claude Code 예시 | 그 밖의 도구 |
|---|---|---|
| 가벼운 모델 | haiku | 각 도구의 가벼운 모델 |
| 표준 모델 | sonnet | 각 도구의 표준 모델 |
| 가장 강한 모델 | opus | 각 도구의 상위 모델 |

## 9. 리뷰 범위 규칙

- 크기 기준은 폐기했다. 크기로 절차나 위임을 나누지 않고, 리뷰 범위를 정할 때도 쓰지 않는다.
- 용어: 판정(PASS/미달)은 리뷰 1회의 결과다. 체크리스트 항목별 결과는 '통과 항목'과 '미달 항목'으로 부른다.
- 재리뷰는 직전 리뷰 이후 변경분과 직전 리뷰의 미달 항목만 본다. 직전 리뷰의 통과 항목은 다시 보지 않는다. 작업 단위가 끝나면 작업 전체를 한 번 리뷰한다.

## 10. 미결정·결정 사항
