# agent-snap 프로젝트 하네스 (프로젝트 규칙 정본)

- 정본 위치: `harness/PROJECT_RULES.md`
- 적용 범위: 이 프로젝트(agent-snap)에만 적용한다. 베이스 하네스(`harness/HARNESS.md`)와 마커 블록은 읽기 전용이고, 이 파일이 그 위로 얹는 오버레이 정본이다.
- 우선순위: HARNESS.md 1절대로 이 파일이 베이스보다 더 엄격한 항목은 우선하고, 완화는 `[안전 예외 승인: N번]`을 명시한 항목만 허용한다.

## 프로젝트 오버레이

[안전 예외 승인: 3번 커밋 — 작업 단위 전체 리뷰 PASS 기록이 있을 때만 로컬 커밋 허용(푸시·병합은 사용자 허락 필수)]

- 흐름은 베이스 하네스의 2단계(구현 서브 → 독립 리뷰 세션)를 따른다. 구현 위임 하나가 끝날 때마다 구현 맥락 없는 새 읽기 전용 리뷰 세션이 review-harness 체크리스트 7항목과 dev-principles 전 항목(2~11절 전체, 테스트 코드 포함)으로 리뷰한다. 메인은 코드리뷰 결과의 근거(파일:라인, 수치)를 직접 확인하고, 지적은 minor까지 고칠지 판단해 고친 뒤 재리뷰한다.
- 커밋 메시지는 한국어로 쓴다. 비밀 값과 `.env`는 커밋하지 않는다.
- 파일 삭제를 요청(승인 창 포함)할 때는 대상 파일과 경로, 정체가 무엇이고 왜 필요한지, 같은 역할을 하는 대체 산출물 경로(파일:라인)를 먼저 적고 나서 삭제를 요청한다. 근거 없이 삭제 창만 띄우지 않는다.
- 서브에이전트 모델은 `harness/HARNESS.md` 8절의 3단계로 고른다: 단순 작업은 가벼운 모델, 구현은 표준 모델, 어려운 설계는 가장 강한 모델. OpenCode는 지금 세션과 같은 모델로만 서브를 열고, 모델 지정 인자를 쓰지 않는다.
- 하네스 문서는 프로젝트 사본 `harness/HARNESS.md`, 프로젝트 규칙 정본은 `harness/PROJECT_RULES.md`, 스킬은 `.agents/skills/`와 `.claude/skills/`에 있다.
- 엔드포인트 주소를 코드와 문서에 넣지 않는다. 키는 사용자 설정 폴더의 `credentials.jsonc`로만 받고 어디에도 값을 남기지 않는다.
- Hugging Face 모델은 용량·라이선스 목록 승인 후에만 받는다.
- 에이전트(M1)를 먼저 완성한다. 판정 모델 작업은 M1 이후, 실제 세션 출력으로만 평가한다.
- 작업마다 논문·자료를 조사해 `docs/RESEARCH.md`(및 단일 작업 문서 `## 리서치 및 설계 근거`)에 기록하고, 적용 위치나 미적용 이유를 남긴다. 링크는 직접 열어 실제로 있는지 확인한 것만 적는다.
- 작업을 시작할 때 관련 논문을 찾아 참고하고, 작업을 기능별 세부 작업으로 나눠 진행한다. 기획 정본은 `docs/plans/`에 두고, 위임용 상세 작업 문서는 `docs/tasks/`에 둔다. 작업 문서에 참고 논문 절과 세부 작업 절이 채워져 있어야 승인을 요청하고, 구현은 세부 작업 하나씩 위임한다.
- 논문 원문과 번역 전문은 `.local/research/`(git 제외, 플랜별 폴더)에 두고, 공개 문서에는 링크와 요약만 둔다.
- 번역은 미리 모아두지 않는다. 플랜 착수 시점에 그 플랜이 채택·채택예정인 논문을 한 편씩 순차로 번역한다(eli5-clarity 문체, 첫머리 300자 요약). 번역이 기획을 막지 않게, 기획·구현 진행을 우선한다.

## 서브에이전트 호출 규격 (고유 — 하네스 3·6절 위임 규칙의 프로젝트 보충)

호출 전 GetDynamicTools로 schema 확인, CallDynamicTool로 호출. 추측 호출 금지, 실패 시 schema를 다시 읽어 고칩니다. AskQuestion의 questions는 배열, 선택지는 id·label 객체. prompt 안 큰따옴표는 \", 역슬래시 경로는 \\.
순차 실행: run_in_background: false(이 프로젝트는 순차), model: inherit, resume 금지. 새로 여는 세션의 지시에는 "첫 동작은 Write 도구 호출"을 명시합니다.
부모의 직접 허용 작업: docs 작성, 게이트 재확인, 실측 조사, 하네스 동기화.
작업 시작 전 부모가 작업 파일을 9절 규격으로 작성합니다(범위·근거 커밋 SHA·파일:라인·산출물·금지 규격·검증 방법·보고 형식). prompt는 delegation-brief의 포인터 샌드위치([앞: 가드레일 6줄] → [중간: 작업 문서·PLAN.md·PROJECT_RULES.md 경로 포인터] → [끝: 자기점검 4줄], 500자 이하)로 보냅니다.

## 개발 규칙

- 크레이트: `snap-core`(라이브러리, 모든 로직)와 `snap-cli`(입출력만 맡는 얇은 실행 파일).
- 모듈은 하나의 책임만 맡는다: config, llm, agent, tools, monitor, session, context. 도구는 `Tool` 트레이트 구현 하나당 파일 하나.
- 제품 소스 파일 하나 = 제품 책임(변경 이유) 하나. 서로 다른 이유로 바뀌는 코드를 한 파일에 섞지 않는다(dev-principles 2절 SRP, harness/HARNESS.md 10절). 구현·리뷰에서 혼재는 major.
- 같은 관심사 파일이 둘 이상일 때만 하위 폴더를 만든다. 파일 하나짜리를 폴더로 감싸지 않는다.
- 위임용 작업 문서는 `docs/plans/` 기획을 따르는 상세 task로 `docs/tasks/`에 하나만 둔다. 별도 brief 파일은 만들지 않고, 위임 프롬프트는 이 문서를 가리키는 포인터만 담는다. `docs/tasks/`는 gitignore.
- 작업 전·중에 관련 `docs/plans/` 문서(상위 문서와 세부 plan·spec·tasks)와 `docs/tasks/` 작업 문서를 확인한다. 착수 때 상태를 `in-progress`로, 단계가 끝나면 plans의 `tasks.md` 체크·완료 메모와 tasks 문서 상태를, 작업 단위 전체 리뷰가 PASS하면 `done`(또는 완료)으로 맞춰 갱신한다.
- 파일·함수·테스트에 줄 수 기준은 두지 않는다. 같은 기준으로 볼 항목은 중복이다: 한 지식·동작이 두 곳에 있으면 함수로 분리해 한 곳에서 부르게 한다. 같은 일을 하는 함수를 다시 정의하지 않는다. 코드리뷰에서 dev-principles 3절(DRY)·6절(이름과 함수) 기준으로 측정한다.
- 오류: 라이브러리는 `thiserror`, 실행 파일만 `anyhow`. 테스트 밖 `unwrap`/`expect` 금지.
- 비밀 값은 Debug 출력에서 가리는 래퍼 타입으로 다룬다.
- 공개 항목에는 문서 주석을 단다. 주석은 한국어로 쓴다.
- 모든 기능에 단위 테스트를 두고, 네트워크 경로는 모의 서버 통합 테스트로 확인한다.
- dev-principles 스킬을 따르며, 지시와 리뷰에는 반드시 경로를 명시해 파일을 읽게 한다: `.agents/skills/dev-principles/SKILL.md` (Claude Code와 Cursor는 `.claude/skills/dev-principles/SKILL.md`). 리뷰 프롬프트에는 2~11절 전 항목을 함께 담는다.
- 지원 대상은 Windows와 Linux 동등이다. 코드는 두 OS에서 먼저 동작하는 이식 가능한 구조로 쓰고, OS 고유 코드는 `#[cfg(windows)]`·`#[cfg(unix)]`로 게이트를 채워 같은 커밋에서 서로 한 번씩 검증한다. Linux에만 붙이고 Windows 기준을 빠뜨리는 잘못을 리뷰에서 막는다.

## 병합(머지) 규칙

- PR의 커밋은 PR에 붙은 CI 검사(매트릭 전체)가 전부 초록(성공)이 아니면 머지하지 않는다. 실패가 하나라도 남아 있으면 develop·main 어느 브랜치에도 병합하지 않는다. 예외는 사용자가 명시적으로 허용한 경우만 인정한다.
- Windows와 Linux를 모두 지원해야 하므로 `ubuntu-latest`·`windows-latest` 두 검사가 모두 초록이어야 한다. 개발 코드는 특정 OS에 의존하지 않고 이식성 있게 짠다. Windows 전용 코드는 `#[cfg(windows)]`로 게이트를 채우고 Linux에서는 `#[cfg(unix)]` 경로를 같은 커밋에서 함께 확인한다.
- 로컬 개발은 지금 OS에서 검증하고, 나머지 OS는 다음 커밋 전 CI 매트릭스로 확인한다.
- 브랜치 이름을 그대로 쓰고, `git merge --no-ff <브랜치>` 또는 PR 머지로 병합 커밋을 남긴다. 개발 커밋의 트리를 대상 브랜치에 그대로 복사해 붙이지 않는다. PR에 붙은 커밋과 대상 브랜치의 머지 커밋을 `git merge-base --is-ancestor <PR head SHA> <대상 SHA>`로 확인한다.

## 문서 규격

- 기획 상태 정본은 `docs/PLAN.md`에 두고, 항목당 한 줄로만 쓴다. 라운드.log 같은 로그를 쌓지 않고, 상태가 바뀌면 그 줄을 갈아엎는다. 상태 셀은 2,000자를 넘기지 않는다.
- 라운드 로그(경위·판정·검증 결과 기록)는 `docs/tasks/<기획 순번>/<세부 순번>-<작업명>/T<번호>-<짧은 이름>.md`에만 둔다. 한 파일에 라운드 절을 둘 이상 두지 않는다. 새 라운드는 앞 라운드를 이어쓰지 않고 파일 상태를 갈아엎어 갱신한다.
- 하네스 설치·업데이트 작업 문서는 `docs/tasks/update-harness/<번호>-<작업명>/`에 둔다.
- 작업 파일은 `docs/tasks/01/`(기획 01), `docs/tasks/02/`(기획 02)처럼 기획 순번 폴더 안에 그 기획의 세부 순번 폴더로 담는다. 폴더 이름의 순번은 항상 두 자리로 쓰고(예: 01, 02, …, 09, 11), 예: `docs/tasks/02/02-config/T1-config-read.md`.
- `docs/plans/` 하위 세부 기획 폴더도 같은 규칙을 따른다. 예: `docs/plans/02-client/02-04-retry/`. 문서 안 참조·링크도 폴더 이름과 같은 표기로 맞춘다.
- 기획 문서(`plan.md`)에는 `## 작업계획` 표를 둔다. 열은 `작업 | 범위 | 금지 | 산출물 | 검증 명령`을 포함하고(선행 작업 열을 더할 수 있다), 행 이름은 `T<번호> <작업명>`으로 쓴다. 행 하나가 상세 작업 파일(T-파일) 하나와 대응한다.
- 기획 문서(`plan.md`)에는 `## 작업 파일` 표를 둔다. 열은 `파일 | 작업 | 상태`이고, 파일 칸에 상세 작업 파일 경로(`docs/tasks/<기획 순번>/<세부 순번>-<작업명>/T<번호>-<짧은 이름>.md`)를 적는다. 상태는 계획 / 진행 / 완료 / 막힘 중 하나다. 상세 작업 파일의 상태가 바뀔 때마다 이 표의 상태 셀을 같은 내용으로 함께 고친다. 두 곳이 다르면 상세 작업 파일이 기준이고 표를 맞춘다.
- 상세 작업 파일(T-파일) 필드는 목표, 근거(기획 문서의 결정·AC 번호), 읽을 파일, 할 일(단계 목록), 검증(게이트 이름·명령·로그 경로), 완료 조건, 상태(계획 / 진행 / 완료 / 막힘), 라운드 보고(하나만)로 한다. 상세 작업 파일에는 결정 문서 본문을 복제하지 않고 절 번호와 원천 포인터(파일:줄)만 적는다.
- 상세 작업 파일(T-파일)의 읽을 파일에는 `harness/HARNESS.md`, `AGENTS.md`, `.agents/skills/dev-principles/SKILL.md`(Claude Code·Cursor는 `.claude/skills/dev-principles/SKILL.md`), `harness/PROJECT_RULES.md` 개발 규칙 절을 반드시 넣는다. 할 일 단계에는 "dev-principles 2~11절(SRP 파일·함수 분리, DRY 재사용 사다리) 준수"와 "서로 다른 책임을 한 파일에 몰아넣지 않고 역할별 파일로 분리" 단계를, 완료 조건에는 "dev-principles 2~11절 준수 확인과 파일 분기 구조"를 반드시 적는다. 검증에는 게이트 이름·명령·로그 경로를 적는다.
- `docs/plans/**/tasks.md`는 구현 단계 목록·테스트 계획·DoD를 담은 문서로 두고, 단계마다 "확인:"으로 검증 단계를 적는다.
- 리뷰 기록은 `docs/reviews/`에 기획 순번 폴더(예: `docs/reviews/02/`, `docs/reviews/update-harness/`)로 같은 구조로 둔다. 파일 이름에서 기획·세부 접두사를 빼고 폴더로 계층을 나타낸다.
- 게이트(검사) 결과는 게이트 이름, 종료 코드, 로그 경로, 대상 파일 SHA256, 시작·끝 시각으로 기록한다. 대상 파일의 SHA256이 그대로면 같은 결과를 다시 쓰지 않고 재활용한다.
- `.local/` 임시 로그는 결과가 리뷰 기록에 확정되면 즉시 지운다. 하네스가 허용하는 `.local/` 산출물은 검증 로그(리뷰·PASS 확정 후 삭제), `.local/research/`(논문 원문, 상주), 문서 정리 백업(정리 완료 후 삭제)이며, 이 셋 외 파일은 두지 않는다. 로그를 남기는 규칙(HARNESS.md 108절)과 함께 확정 후 삭제가 기본이다.
- 문서에 경로를 쓸 때 이동한 뒤에는 연결(상대 경로)을 새 위치에 맞게 고치고, `docs/INDEX.md`·`docs/DECISIONS.md`·`docs/RESEARCH.md`의 가리키는 곳을 함께 갱신한다.
