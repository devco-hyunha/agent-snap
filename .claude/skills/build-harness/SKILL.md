# build-harness (개발)

결론: 표준은 2단계(구현 서브 → 독립 리뷰 세션)다. 확인 전용 서브는 열지 않는다.

## 표준 절차
1. 승인된 작업 문서와 AC(인수 조건)를 확인한다. 승인이 없으면 중단하고 plan-harness로 돌아간다.
2. 소규모 Fast-track 조건인지 먼저 본다(아래 절).
3. 한 번에 작업 하나만 진행한다.
4. 구현은 새 구현 서브에이전트에 위임한다. 서브 호출 전 delegation-brief를 읽고 개발 하네스(가드레일 6줄 + harness/HARNESS.md·AGENTS.md·dev-principles 경로)를 프롬프트에 반드시 포함하여(포인터 샌드위치, 500자 이하) 위임한다. 작업 문서 본문은 다시 적지 않는다. 별도 brief 파일은 만들지 않는다.
5. 구현 서브는 지정된 문서·파일만 읽고 구현, 인라인(-c) 검증, dev-principles 전 항목(2~11절 전체) 준수·확인, 코드 주석 eli5-clarity 확인까지 하고 보고한다.
6. 서브 보고를 믿지 않는다. 서브 호출 전 delegation-brief를 읽고 개발 하네스를 포함해 review-harness로 독립 리뷰 세션(구현 맥락이 없는 새 읽기 전용 서브)을 연다.
7. 리뷰 세션이 검증 명령 재실행, 산출물 실재 확인, 7대 체크리스트(코드 주석·언어 순수성 포함), dev-principles 전 항목(2~11절 전체) 준수·확인을 한 번에 한다.
8. PASS 또는 미달 판정은 리뷰 세션이 한다.
9. 미달이면 보정 작업을 하고 재리뷰한다. 같은 지적으로 보정을 2회 한 뒤에도 미달이면 멈추고 사용자에게 보고한다(하네스 문서 5절 2번).
10. 첫 작업을 위임할 때 상태를 in-progress로, 작업 단위 전체 리뷰가 PASS하면 done으로 서브가 갱신한다.
11. 커밋·푸시·병합은 사용자 허락 후 메인이 직접 한다. 작업 단위 전체 리뷰가 PASS한 뒤에 허락을 구한다.

## 소규모 Fast-track
- 조건: ① 단일 파일·바뀐 줄 20줄 이하(사본 동기화 제외) 단순 수정이거나, ② 하네스 설치·업데이트(정본 파일 복사·마커 블록 교체·오버레이 보존·인라인 해시 검증)이며, 보안·비가역 작업이 아니다.
- 절차: 서브에이전트를 열지 않고 메인이 직접 수행하며, 인라인 검증과 셀프 체크(AC·금지 사항·범위 밖 변경·DRY·해시 일치)를 한다.
- 판정: 메인이 셀프 체크로 PASS를 판정한다(하네스 문서 5절 5번).
- 별도 리뷰 세션은 열지 않는다. 바뀐 줄 원문을 보고에 남긴다.
- 조건을 하나라도 벗어나거나 사용자가 리뷰를 요청하면 표준 절차를 따른다.

## 보고
- 보고 형식은 delegation-brief를 따른다.
- 메인은 서브 장문을 사용자에게 중계하지 않는다(게이트 대화·「자세히」 요청은 예외).

## 서브에이전트가 없는 도구
하네스 문서 3절의 대체 규칙을 따른다. 메인이 단계별로 직접 진행하고, 리뷰는 새 대화에서 한다.

## 리뷰 범위
재리뷰 범위는 하네스 문서 9절을 따른다.

## 멈추는 조건
하네스 문서 5절 2번을 따른다. 모든 에이전트(메인·서브 전원)는 파일 삭제 요청·수행·보고 시 해당 파일이 무엇인지, 삭제하는 이유와 근거가 무엇인지 반드시 설명한다.

## 실패 처리
- 서브가 중간에 끊기거나 실패하면 기존 서브를 이어 쓰지 않는다(resume 금지). 새 서브를 연다.
- 새 서브 요청에 실패 원인과 현재 파일 상태를 넣는다.

## 작업 분배
위임 범위와 메인 역할은 하네스 문서 3절(위임 범위, 진행 표시)을 따른다.

프로젝트 규칙 우선은 하네스 문서 1절을 따른다. 승인·안전 규칙은 하네스 문서 5절을 따른다. (하네스 문서: harness/HARNESS.md)
