# 개발 원칙

각 원칙은 정의 / 판단 기준 / 위반 예 순서로 적는다.

## 1. 적용 우선순위

- 프로젝트의 CLAUDE.md, AGENTS.md, docs 등 프로젝트 규칙이 있으면 그것을 먼저 따른다.
- 이 스킬은 프로젝트 규칙이 다루지 않는 부분의 기본 기준으로만 쓴다. 프로젝트 규칙 우선은 하네스 문서 1절을, 승인·안전 규칙은 하네스 문서 5절을 따른다. (하네스 문서: harness/HARNESS.md)

## 2. SOLID

**SRP (단일 책임)**
- 정의: 모듈과 클래스는 변경 이유가 하나여야 한다.
- 기준: 서로 다른 이유로 수정될 코드가 한 파일에 섞여 있지 않은지 본다.
- 위반: 주문 클래스가 가격 계산, DB 저장, 이메일 발송을 모두 한다.

**OCP (개방-폐쇄)**
- 정의: 확장은 기존 코드 수정 없이 가능해야 한다.
- 기준: 새 유형을 추가할 때 기존 분기문을 고쳐야 한다면 재검토한다. 변형이 실제로 둘 이상일 때만 적용한다.
- 위반: 결제 수단이 늘 때마다 거대한 if/else 체인에 분기를 추가한다.

**LSP (리스코프 치환)**
- 정의: 하위 타입은 상위 타입의 계약을 깨지 않아야 한다.
- 기준: 하위 타입을 상위 타입 자리에 넣었을 때 호출부가 타입을 따로 확인해야 하면 위반이다.
- 위반: 상위 타입의 메서드를 하위 타입이 예외로 막거나 사전조건을 강화한다.

**ISP (인터페이스 분리)**
- 정의: 쓰지 않는 메서드에 의존하지 않도록 인터페이스를 작게 나눈다.
- 기준: 구현체가 빈 메서드나 예외만 던지는 메서드를 갖고 있으면 쪼갠다.
- 위반: 읽기만 하는 소비자가 쓰기, 삭제 메서드까지 가진 인터페이스를 받는다.

**DIP (의존 역전)**
- 정의: 고수준 모듈은 구체 구현이 아니라 추상에 의존한다.
- 기준: 비즈니스 로직이 DB 클라이언트나 HTTP 라이브러리를 직접 생성하면 주입으로 바꾼다.
- 위반: 서비스 함수 안에서 특정 DB 드라이버를 직접 import해 연결한다.

## 3. DRY

- 정의: 같은 지식은 한 곳에 둔다.
- 기준: 한쪽을 고치면 다른 쪽도 반드시 고쳐야 하는 중복이면 합친다. 우연히 비슷한 코드는 성급히 합치지 않고, 세 번째 중복부터 추출을 검토한다.
- 위반: 같은 검증 규칙이 세 곳에 복사되어 있어 한 곳만 고쳐 불일치가 생긴다.

## 4. KISS와 YAGNI

- 정의: 지금 필요한 만큼만 단순하게 만든다.
- 기준: 요청되지 않은 추상화, 설정, 확장 지점은 만들지 않는다. 더 단순한 방법이 있으면 그쪽을 택한다.
- 위반: 사용처가 하나뿐인데 팩토리, 플러그인 레지스트리, 설정 옵션을 미리 만든다.

## 5. 관심사 분리와 응집·결합

- 정의: 입출력, 비즈니스 로직, 저장소 접근을 분리하고, 모듈 간 의존은 적게 유지한다.
- 기준: 비즈니스 로직을 HTTP나 DB 없이 단독으로 테스트할 수 있는지 본다. 관련 있는 코드는 한 모듈에 모은다.
- 위반: 요청 핸들러 안에 SQL과 가격 계산이 함께 있다.

## 6. 이름과 함수

- 정의: 이름만 보고 동작을 알 수 있어야 하고, 함수는 한 가지 일만 한다.
- 기준: 이름에 "그리고"를 넣어야 설명되면 쪼갠다. 불리언 매개변수 대신 별도 함수나 명명된 옵션을 쓴다. 깊은 중첩보다 early return을 쓴다.
- 위반: `process(data, true, false)`처럼 호출부에서 의미를 알 수 없다.

## 7. 에러 처리

- 정의: 실패를 숨기지 말고 구조화해서 드러낸다.
- 기준: 빈 except/catch는 금지한다. 잡았다면 처리, 변환, 기록 중 하나는 한다. 입력 검증은 외부 입력이 들어오는 경계에서 한다.
- 위반: `catch (e) {}`로 삼키고 성공한 것처럼 계속 진행한다.

## 8. 보안 기본

- 정의: 신뢰할 수 없는 입력과 비밀 정보를 안전하게 다룬다.
- 기준: 시크릿과 키를 코드나 커밋에 넣지 않는다. 셸 명령은 문자열 결합 대신 인자 배열로 실행하고 외부 입력을 신뢰하지 않는다. 경로 입력은 허용 범위 밖(`..`, 절대경로, 심볼릭 링크 탈출)을 막는다.
- 위반: `exec("git log " + userInput)`, 또는 API 키를 소스에 하드코딩한다.

## 9. 테스트

- 정의: 동작을 검증하는 테스트를 코드와 함께 둔다.
- 기준: 버그 수정은 재현 테스트부터 작성한다. 테스트는 구현 세부가 아니라 외부에서 관찰되는 동작을 본다.
- 위반: 내부 private 함수 호출 순서를 검증해서 리팩터링할 때마다 테스트가 깨진다.

## 10. 주석과 정리

- 정의: 주석은 "무엇"이 아니라 "왜"만 쓴다.
- 기준: 미사용 코드와 죽은 import는 삭제한다. 요청 범위 밖을 몰래 고치지 않고, 필요하면 따로 알린다.
- 위반: `// i를 1 증가` 같은 주석, 주석 처리된 옛 코드, 요청과 무관한 대규모 포맷 변경.

## 11. 작업 방식

- 변경 전에 영향 범위(호출부, 의존하는 모듈, 테스트)를 확인한다. (위임 시에는 작업 문서의 파일 범위 안에서)
- 변경 후에 빌드와 테스트로 확인한다.
- 확인하지 못한 것은 확인하지 못했다고 말한다.
