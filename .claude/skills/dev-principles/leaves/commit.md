# 12. 커밋 메시지와 절차

- 정의: 커밋 제목·본문 형식과 실행 절차의 정본이다. 메인이 사용자 허락 후 커밋할 때만 읽는다.
- 기준: 허락(하네스 5절 3번) 전후에 이 잎을 따른다. 푸시·병합 허락은 별도다.
- 위반: 형식 없이 한 줄만 대충 쓰거나, 허락 전·훅 건너뛰기·시크릿 포함 커밋.

## 메시지 형식

1. 제목 한 줄(대략 50~72자): `유형(선택스코프): 한국어 한 줄`
   - 유형 허용: `feat` `fix` `docs` `refactor` `test` `chore` `perf`
   - 스코프는 필요할 때만(`feat(harness): …`)
   - 초점은 **왜**(또는 왜가 드러나는 결과). 파일 나열·무엇을만 쓰지 않는다.
2. 본문(범위가 넓거나 이유가 여럿이면 **필수**, 제목만으로 충분하면 생략):
   - 첫째 단락: 한국어로 **요약**(왜·결과)
   - 빈 줄 한 줄
   - `-` 목록으로 **상세**(바뀐 점·근거). 한 줄에 포인트 하나.
3. 존댓말·사용자 언어·한자·외국어 서술 금지는 하네스 1절과 같다. 코드·경로·명령·식별자는 원문.
4. 비밀 값·`.env`는 메시지·본문에 넣지 않는다.

예(제목+본문):

    feat(harness): 커밋 메시지 규칙을 잎 정본으로 둡니다

    에이전트가 제목·본문 형식을 같게 쓰게 하기 위함입니다.

    - 형식·절차를 leaves/commit.md로 옮겼습니다
    - HARNESS·스킬은 잎 포인터만 둡니다

제목만으로 충분한 예:

    docs: INDEX에 007 작업 행을 추가합니다

## 실행 절차

사용자 **명시 허락** 후에만 한다(하네스 5절 3번). 메인이 직접 실행한다.

- `git config` 변경 금지. 훅 건너뛰기(`--no-verify` 등) 금지(사용자가 명시한 때만).
- 파괴적 git(강제 푸시·`hard reset` 등)·메인/`master` 강제 푸시는 사용자가 명시한 때만. 요청이어도 메인/`master` 강제 푸시는 먼저 경고.
- `--amend`는 사용자 명시(또는 훅이 같은 HEAD를 고친 경우)·이 대화에서 만든 HEAD·미푸시일 때만. 훅 거절·실패 후 amend 금지. 이미 푸시됐으면 사용자 명시 없이 amend 금지.
- 커밋 전 병렬: `status` / staged·unstaged `diff` / 최근 `log`(메시지 톤 맞춤).
- 시크릿·`.env` 등 위험 파일은 스테이징하지 않는다. 사용자가 넣으라 해도 경고.
- 메시지에 **왜**가 드러나게 쓰고, HEREDOC(또는 동등한 여러 줄 안전 전달)으로 본문을 넘긴다.
- 순서: 관련 파일 stage → commit → `status`로 확인. 빈 커밋 금지.
- 푸시는 별도 허락. 대화형 git(`-i`) 금지.
