# plan-harness (기획)

결론: 승인된 작업 문서가 생기기 전에는 코드를 쓰지 않는다.

## 절차
- 서브에이전트(규칙 확인, 리서치, 작업 문서 기록) 호출 전 delegation-brief를 읽고 개발 하네스(가드레일 6줄 + harness/HARNESS.md·AGENTS.md·dev-principles 경로)를 프롬프트에 반드시 넣어 위임한다.
1. 프로젝트 규칙을 확인한다. AGENTS.md의 ## 프로젝트 오버레이 절, docs/PROJECT_RULES.md, docs/INDEX.md, CLAUDE.md가 대상이다. 읽기는 서브에이전트에 맡기고 결과를 반영한다.
2. 조건부 논문·기술 리서치(Research Gate): 아래 조건 중 하나에 해당할 때만 한다.
   - ① 사용자가 논문·리서치·벤치마크 조사를 요청했다.
   - ② 알고리즘·AI/ML·양자화·오디오/영상·성능·아키텍처 선정처럼 학술·기술 근거가 설계 결론을 바꾼다.
   - ③ 오버레이(AGENTS.md 또는 docs/PROJECT_RULES.md)에 [기획 리서치: 필수]가 있다.
   - 단순 기능 수정·UI·문서 작업은 생략해 토큰을 아낀다.
   - 메인이 직접 검색하지 않는다. 읽기 전용 리서치 서브(표준 모델)에 맡기고, 출처 링크·핵심 수치·교훈·채택/기각 근거만 짧게 보고받는다.
   - 보고는 작업 문서의 ## 리서치 및 설계 근거에 기록한다.
3. 오버레이가 안전 규칙을 바꾸면 방향을 가린다. 더 엄격하면 따른다. 완화는 [안전 예외 승인: N번]이 있을 때만 따른다(하네스 문서 1·5절).
4. 요구 수렴: 결론을 바꾸는 질문만 최대 3개 한다(게이트 대화). 나머지는 가정으로 적고 진행한다. 중간 설명은 한 줄 이하.
5. 작업 문서를 쓴다. 메인이 내용을 정하고 서브에이전트가 기록한다. 프로젝트에 정해진 위치가 있으면 그곳을 따르고, 없으면 docs/tasks/<순번>-<작업명>.md.
6. 작업을 나눌 때 각 작업에 DoD(완료 정의: AC 충족, 검증 통과, 리뷰 PASS를 모두 만족한 상태)를 부여한다.
7. 기획 승인 전에는 코드를 쓰지 않는다.

## 소규모 Fast-track 예외
- 조건: 단일 파일, 바뀐 줄 20줄 이하(사본 동기화 제외), 단순 수정이며 보안·비가역 작업이 아니다.
- 이 조건이면 작업 문서와 AC를 만들지 않는다. 메인이 직접 수정한다. 절차는 build-harness를 따른다.
- 조건을 하나라도 벗어나면 위 절차로 돌아온다.

## 작업 문서 필드
이 문서가 위임의 유일한 작업 문서다. 별도 brief 파일은 만들지 않는다(delegation-brief).
- 목적
- 리서치 및 설계 근거 (조건부 필수: 2번 조건 해당 시)
- 범위(In)
- 비범위(Out)
- 설계 요약: 작업별 절마다 범위·금지 사항·산출물·검증 명령을 적는다. 서브가 이 절만 읽고 일한다. 파일 삭제가 포함되면 해당 파일이 무엇인지, 삭제 이유와 근거가 무엇인지 반드시 명시한다.
- AC(인수 조건): 체크 가능한 조건 3~7개. Given/When/Then 또는 EARS 형식.
- 테스트 계획
- 문서 영향 (갱신해야 할 문서)
- 리스크
- 상태: planned / in-progress / done

## 작업 단위
작업 단위는 작업 문서 하나다. 크기로 나누지 않고 모든 계획을 같은 방식으로 작업 단위로 나눈다.
