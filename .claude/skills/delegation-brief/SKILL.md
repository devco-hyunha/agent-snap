# delegation-brief (서브에이전트 요청 규격)

## 원칙
서브는 대화 맥락을 보지 못한다. 구현·보정 위임은 요청을 두 경로로 전달한다.
- (a) 작업 문서 파일
- (b) 자체 포함 프롬프트 (프롬프트만 읽어도 작업할 수 있어야 한다)

작업 문서 파일은 구현·보정 위임에만 필수다. 읽기·검색·기록·확인·리뷰 서브는 자체 포함 프롬프트만 쓴다.

## 위임용 작업 문서 필수 섹션
기획용 작업 문서(plan-harness)와 다른 문서이며, 기획용 문서를 바탕으로 만든다.
목적 / 서브 보고에서 채택한 근거(출처 포함) / 작업 범위 / 금지 사항 / 산출물 / 검증 방법 / 보고 형식.
저장 위치: 프로젝트에 정해진 위치가 있으면 그곳, 없으면 기획용 작업 문서 옆에 docs/tasks/<순번>-<작업명>.brief-<번호>.md
금지 사항에는 범위 밖 파일 수정·생성 금지, 커밋·푸시 금지, 검증 인라인(-c) 실행(임시 스크립트 파일 금지), 임의 코드 샘플 금지를 포함한다.
보정 작업이면 "변경하지 않는 것"을 추가한다.

## 브리프 출력 규칙
- 사용자가 브리프를 요청하면 위임용 작업 문서 파일을 만들지 않습니다.
- 프롬프트를 markdown 코드 블록으로 채팅에 띄워 복사용이 있게 합니다.
- 항목·공통 지시·하네스 문서 경로를 모두 담아, 붙여 넣는 곳(새 대화·새 서브)에서 단독으로 작업할 수 있는 자체 포함으로 만듭니다.
- 브리프를 조립할 때 하네스 문서의 공통 지시 5개와 필수 문안(원문 유지, 프로젝트 규칙 우선, 승인·안전)을 빠짐없이 담습니다.
- 브리프 본문과 사용자에게 띄우는 문장은 사용자가 사용하는 언어로 씁니다.
- 브리프 끝에 바뀐 파일 목록을 git status로 확인해 붙입니다. 읽기 전용 확인이 허용되며, 확인은 브리프를 조립하는 서브가 합니다.

## 프롬프트 필수 항목
- 작업 문서 절대 경로(구현·보정 위임일 때)
- 목적과 범위 요약
- 금지 사항
- 산출물
- 검증 명령
- 보고 형식
- 참고 문서 경로
- 프로젝트 규칙 문서 경로(있으면)

## 프롬프트 공통 지시 5개
1. 쓰기 작업 서브는 작업 문서(없으면 프롬프트)와 거기에 적힌 파일만 읽은 직후 바로 작성·수정한다. 그 밖의 탐색은 하지 않는다. 읽기 전용 서브에는 적용하지 않는다.
2. 도구 호출 문법을 본문 텍스트로 쓰지 않는다.
3. 모든 보고는 사용자가 쓰는 언어로, 정중한 존댓말을 유지한다.
4. 실패하면 즉시 멈추고 실패 원인과 현재 파일 상태를 보고한다.
5. 프롬프트 본문은 사용자가 사용하는 언어로 쓴다. 보고와 지시가 같은 언어다.

공통 지시 5개와 별도로, 프롬프트에 다음 두 줄도 넣는다.
- 원문 유지 원칙은 하네스 문서 1절을 따른다.
- 프로젝트 규칙 우선은 하네스 문서 1절을, 승인·안전 규칙은 하네스 문서 5절을 따른다. (하네스 문서: harness/HARNESS.md)

## 단순 위임 기준
- 단순 위임: 한 서브 호출로 끝나는 읽기·검색·기록·확인 작업입니다. 잡음이 남는 파일 읽기·수정·쓰기는 서브에 맡기고 짧은 명령 한 줄 실행(git status·log·diff, 커밋, 푸시, python -c 인라인 검증)는 허락을 받아 메인이 직접 실행하는 것이 하네스 문서 3절의 위임 규칙입니다.
- 합침: 작을 때 여러 개를 한 서브 호출에 합치고 프롬프트는 한 번만 씁니다. 합쳐도 작업 범위는 한 목적을 담습니다.
- 모델: 하네스 문서 8절의 가벼운 모델을 지정합니다.
- 부모 보호: 서브는 자기 창를 쓰므로 서브의 파일 읽기·검색 잡음은 부모에 남지 않습니다. 부모에 남는 것은 지시와 짧은 보고뿐이며, 보고는 보고 형식 절의 짧은 요약을 따릅니다.
- 메인 예외: 메인은 정본(하네스 문서·SKILL.md)을 직접 읽습니다(3절).
## 소규모 구현
- 소규모 구현: 한 문서의 한 자리 한 줄 보정, 바뀐 줄 합계 10줄 이하(사본 동기화 포함). 파일 총줄 수 상한은 두지 않는다. 서브는 대상 위치가 속한 절만 읽고 편집과 인라인 검증을 한 호출에 한다.
- 서브는 바뀐 줄 원문을 보고에 남긴다. 메인이 바뀐 줄을 읽고 확인한다. 작업 문서와 AC는 만들지 않는다. 리뷰는 열지 않는다. VERSION은 커밋 시점에 올린다.

## 모델 선택
모델 선택은 하네스 문서 8절을 따른다.

## 보고 검증
서브 보고는 확인 전용 서브가 확인하고 메인이 판단하는 것을 전제로 한다.

## 이스케이프
긴 프롬프트를 JSON 등 구조화 도구에 넣을 때는 해당 이스케이프 규칙을 따른다. 서브에이전트 호출 방식이 일반 문자열이면 해당 없다.

## 리뷰 위임 프롬프트 템플릿
리뷰 서브는 프롬프트만 읽는다. 아래 9항목을 프롬프트에 그대로 담는다:
1. 읽기 전용 선언: 리뷰 서브는 파일을 수정하지 않고 문제만 기록한다.
2. 체크리스트 6항목 원문: ① AC 충족 ② 금지 규격 위반 ③ 검증 명령·로그 근거 ④ 에러 처리·보안 기본 ⑤ 문서 동기화 ⑥ 범위 밖 변경.
3. AC 원문과 금지 사항, 위임용 작업 문서가 있으면 그 절대 경로를 담는다.
4. 판정 기준 발췌: critical/major 유무로만 판정하고, minor만 있으면 PASS한다.
5. 산출물 형식: 문제 목록(파일:라인, 심각도, 내용), 판정 PASS/미달.
6. dev-principles 경로를 담는다.
7. 하네스 문서 경로를 두 줄로 담는다: 원문 유지 원칙은 하네스 문서 1절을, 승인·안전 규칙은 하네스 문서 5절을 따른다. (하네스 문서: harness/HARNESS.md)
8. 재리뷰인 경우 직전 리뷰의 통과 항목 목록, 미달 항목·지적 목록, 바뀐 파일 목록을 담는다.
9. 구현 맥락이 없는 새 세션임을 명시한다.
